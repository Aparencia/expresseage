## 5. R-A1-16 · 截图票据"一次性"实为事务外校验（P3）

### 5.1 三态与结论
**成立**。静态机制 + 构造交错探针均支持；顺序控制组证明"唯一的闸是事务外那次读"。

### 5.2 入口 → 传播 → 终点

- **入口** `handlers/order/_store.js:286-298` `loadUploadTicket`：`:291` `if (ticket.usedAt || ...) throw invalidState` —— **事务外**判断。
- **传播** `handlers/order/_create.js:174-189` `prepareImage`：在 `createOne/createBatch` 的**建单事务之前**调用 `loadUploadTicket`。
- **终点** `handlers/order/_create.js:385-387`（`createOne` 事务内）与 `:464-466`（`createBatch` 事务内）：`await trx.update(COLLECTIONS.UPLOAD_TICKETS, imageCtx.ticket._id, { usedAt: nowDate })` —— **无 `where: {usedAt: null}` 条件、不断言 `updated === 1`**。
- 能力对照：`db/dao.js:115-121` 已提供 `updateWhere`（返回 `{updated}`）；命令 `Select-String -Path cloudfunctions\api\handlers\order\_create.js -Pattern 'UPLOAD_TICKETS|updateWhere'`（退出码 0）→ 仅 386 / 465 两处无条件 `trx.update`，`updateWhere` **0 命中**。

### 5.3 探针：顺序控制组 vs 构造交错组

```text
[C.sequential.first] {"ok":true,"code":"","orderNo":"20261022-0001"}
[C.sequential.second] {"ok":false,"code":"INVALID_STATE","message":"上传凭证已失效，请重新上传"}
[C.interleave.B.create] {"ok":true,"code":"","orderNo":"20261022-0001"}
[C.interleave.A.create] {"ok":true,"code":"","orderNo":"20261022-0002"}
[C.interleave.ordersCount] 2

```

- 顺序组：第二次用同一票据立刻被 `INVALID_STATE` 拦下（说明预检本身有效）；
- 交错组：A 完成事务外预检后、其建单事务开始前，插入 B 的**完整** `order.create`（同一票据、不同 `clientRequestId`）→ B 落单并写 `usedAt`，A 的事务仍成功建单并再次写 `usedAt` → **两单共用同一截图路径**，票据只被记一次消费。

### 5.4 方法学声明（诚实边界）

- `tools/fake-db.js` 是内存 fake DB，事务无隔离与并发交错语义（仓内 `TD-015` 已登记该差异）。本探针是**人工构造的交错**（在 A 的 handler 事务入口处启动 B 的完整请求），**不等价于真实云 DB 的并发复现**。
- 但它证明的恰恰是缺陷本质：**校验在事务外**（读到旧值后不再复核）+**事务内更新无条件**（无 `usedAt: null` 谓词）→ 真实并发下"两个请求都在 usedAt=null 时读到票据"这一 TOCTOU 窗口成立；真实环境并发冒烟仍建议按 A1 §5 ② 列入 RUNBOOK。
- 该探针的构造前提是"恰好 A 的 handler 事务是本次请求的第 2 个事务（第 1 个是 ratelimit 计数事务）"，探针内已打印 `txCount=4`（A：ratelimit + handler；B：ratelimit + handler）以便复核。

### 5.5 严重度 / 修复建议

- **维持 P3**：不越权、无重复数据外泄、重复单可取消；破坏"票据一次性"审计口径。
- 同意 A1 修复：事务内 `trx.updateWhere(UPLOAD_TICKETS, { _id: ticket._id, usedAt: null }, { usedAt: nowDate })` 并断言 `updated === 1`，否则 `INVALID_STATE`；`createBatch` 在同一事务内只做一次并同样断言。
