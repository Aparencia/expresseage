## D1 · 后端形态（**开工门 1**）

**背景**：v3 是纯本机台账（无后端、无账号、不跨设备）。v4 需求要求顾客下单、订单进度可跟踪、顾客绑定兼职、兼职数据隔离——订单必须从顾客手机到达兼职手机；开发者后台与只读视角也必须有服务端。纯本地无法满足。

**选项**
- **A（推荐）微信云开发**：云函数 + 云数据库 + 云存储，openid 天然身份，零服务器运维，与小程序同生态。
- B 自建后端：需要 HTTPS 域名、备案、服务器运维、鉴权/防刷全自建，成本与周期明显更高。
- C 纯本地无后端：只能做"同一台手机上的双角色演示"，无法真实面向客户，**不满足需求**。

**推荐**：A。
**理由**：1) 需求本身是跨账号业务，必须有服务端；2) 云开发不需要运维与域名备案（仍需要小程序主体与类目合规）；3) openid 直接用作身份，鉴权链路最短；4) 个人开发者节奏，自建后端成本不划算。
**代价如实记**：1) 数据从"只存本机"变成"存云端"，**隐私承诺与隐私指引必须重写**；2) 依赖云开发配额与冷启动，弱网体验要专门设计；3) 开发前必须由你在微信开发者工具里开通云开发并创建环境（agent 做不了）；4) 换环境/迁移数据需要额外脚本。
**被否**：B（成本/备案/运维不划算）；C（不满足需求）。
**开工门**：你确认 A 并在开发者工具里开通云开发、把环境 ID 告诉 agent（或先建 dev 环境）。

## D2 · appid 与数据命名空间（**开工门 2**）

**背景**：v1/v2/v3 共用 appid `wxcb7e5b41b89bc806`，同一台手机上共享 storage 命名空间（v3 靠换键隔离，有数据红线）。v4 模板 `project.config.json` 里的 appid 是 **`wxf98c87a293092ef5`**（与 v3 不同）。
**选项**
- **A（推荐）使用 `wxf98c87a293092ef5`（v4 模板已有）**：全新 appid ⇒ 独立 storage、独立云开发环境、独立隐私声明与审核；v3 旧小程序可并存不互相干扰。
- B 沿用 v3 appid：storage 与 v3 同命名空间（又回到"三键共存"红线）；隐私声明/审核要在同一 appid 上重来；且本地 v3 数据仍无法跨设备。
**推荐**：A。
**理由**：v4 是面向客户的新产品形态，隐私声明/类目/名称都要重新走审核；新 appid 彻底去掉误写 v3 数据的风险；v3 保留作只读参照。
**代价如实记**：1) v4 **读不到 v3 的本地数据**（新 appid 独立命名空间）⇒ 老客户资料不能自动迁移，只能手工重录/另立导入卡（见 D11）；2) 新 appid 需要重新配置云开发环境与后台隐私声明。
**被否**：B（回到同命名空间红线、审核重来、收益低）。
**开工门**：你确认 `wxf98c87a293092ef5` 就是 v4 要用的 appid（若你其实想沿用 v3 appid，现在说，越晚改代价越大）。

## D3 · 兼职人员如何获得访问权（**开工门 3**）

**背景**：需求原文"兼职人员需要由开发者提供的特定数据才能进行访问"；二次修订明确开发者负责"**邀请码的生效控制**"。
**选项**
- **A（推荐）邀请码**：开发者在后台生成 12 位一次性邀请码（可设有效期 24h/72h/7d/30d、可作废、备注/批次），兼职输入后 openid 绑定为 partner 并分配 `partnerNo`。开发者后台可批量生成/复制/作废/查看状态与使用人。
- B openid 白名单：开发者手工把兼职 openid 填进云函数环境变量；无法批量、无法自助发放、每次加人改配置重部署。
- C 硬编码密钥/口令：写在前端或代码里，可被反编译，**禁止**。
**推荐**：A。
**理由**：1) 可批量、可过期、可作废、有审计；2) 兼职只需拿到一串码，不暴露任何平台配置；3) 符合"由开发者提供特定数据"的原意；4) 开发者后台是本期的必要页面（用户需求 3），不是 P1。
**代价如实记**：1) 邀请码泄露=未授权兼职，需靠一次性+有效期+作废+审计兜底；2) 兼职换微信号需重新发码；3) "生效控制"不提供重新生效——过期/已用/作废只能重新发码。
**被否**：B（运维不可持续）；C（安全红线）。
**落了什么（v0.7）**：`invitation_codes` 集合 + `partner.activate({invitationCode})` + 激活页 + 开发者后台邀请码页 + `INVITE_EXPIRED/INVITE_USED` 错误映射 + 审计（批 2/批 8）。

## D4 · 顾客与兼职的绑定关系

**背景**：需求"顾客和兼职人员绑定，即一个兼职人员不可见另一个的数据，但顾客可以通过绑定对应兼职人员的 id 但不可自主查询其他兼职人员 id"。
**选项**
- **A（推荐）1 顾客同时只绑 1 个兼职**；换绑需先解绑且无进行中订单；兼职可解绑顾客（填原因+通知）。
- B 一顾客可绑多个兼职：下单要选人、隔离规则变复杂、顾客易困惑、兼职间抢单更乱。
**推荐**：A。
**理由**：1) 需求是"绑定对应兼职"，单绑定语义最直接；2) 数据隔离与订单归属简单可验证；3) 一个同学通常只找一个兼职跑；4) 换绑条件保证进行中订单不串人。
**代价如实记**：1) 顾客想换人必须先解绑（有进行中订单时不行）；2) 兼职解绑会让顾客暂时无法下单；3) 兼职"客户数"会因解绑/流失波动。
**被否**：B（复杂度与隔离风险）。
**落了什么**：`bindings` 集合（唯一 ACTIVE 绑定约束）+ 绑定/解绑/换绑流程 + 负向测试；绑定凭据为**完整 `partnerNo`**（见 D15）。

## D5 · 服务目录（**无价格**；已按用户指示关闭）

**背景**：用户 2026-10-21 二次修订明确：本程序只负责顾客下单、兼职接单、信息整理（取件码与站点），**不负责运费计算、价格表等一切**。原 v0.6 的"兼职定价/金额快照/分存"方案作废。
**选项**
- **A（已定）只定义服务类型**：开发者给默认 5 类模板（标准代取/送寝上门/加急代取/代寄/其他代办），兼职启用/停用并设接单范围；订单只快照 `service{code,name}`；**无价格字段、无金额计算、无报价**。
- B 平台统一定价：与"不负责价格表"直接冲突，作废。
- C 顾客自由出价/议价：与零金钱口径冲突，作废。
**结论**：A（用户已定）。
**理由**：1) 用户硬口径优先；2) 服务类型仍足以表达"做什么"，不影响下单/履约/验收；3) 避免任何金额合规与纠纷面。
**代价如实记**：1) 双方费用沟通完全在程序外（本程序不记录、不展示）；2) 未来若要做价格/费用，需另立项目并重新过合规。
**落了什么（v0.7）**：`config.serviceCatalog[{code,name,desc}]`（无价格）+ `partner.serviceConfig.services[{code,enabled}]` + 服务设置页"服务类型与范围" + 零金额门禁（禁止 `price/fee/Fen/金额/价格/运费` 字段与文案）。

## D6 · 金钱与支付（**零交易**；已按用户指示关闭）

**背景**：用户 2026-10-21 二次修订明确：程序**不涉及金钱交易**——不做在线支付、收款、记账、结算，不计算运费，不做价格表等一切。原 v0.6 "线下收款记账 + payStatus + 结算文本"方案全部删除。
**选项**
- **A（已定）零金钱**：程序内不存在任何金额字段、金额计算、支付/收款/结算流程与文案；订单只有状态与信息；用户体验为"下单—接单—取件—送达—完成"。
- B 在线支付：需企业主体+商户号+对账/退款/合规，且与用户硬口径冲突，作废。
- C 线下收款记账：仍会在程序内记录金钱，违反"不涉及金钱交易"，作废。
**结论**：A（用户已定）。
**理由**：1) 用户硬口径优先；2) 去掉支付后，主体/类目与纠纷范围显著缩小；3) 验收可机器扫描"零金额"。
**代价如实记**：1) 程序不提供收款凭证/账单；2) 双方费用相关事宜完全在程序外自理，程序不介入；3) 未来若做支付另立项目。
**落了什么（v0.7）**：删除 `fee/payStatus/markPaid/unmarkPaid/PAYMENT_*`、结算页、收入统计、价格设置、`PRICE_ISSUE/PAYMENT_TIMEOUT` 取消原因、隐私文本金额项；新增零金额门禁 + UI 口径声明"本程序不涉及任何费用收付"。

## D7 · 同寝室 abc 区分标识（roomTag，v0.9 恒大写）

**背景**：需求"后台对同寝室的 abc 区分标识"；v3 的 abc 只是"称呼留空时按同楼栋+宿舍计数自动补名 A/B/C"，不是独立字段、软删会复用、改宿舍会失配（v3 教训 TD-022 残余）。**v0.9 用户四次修订要求"同寝室标识恒大写"。**
**选项**
- **A（推荐）独立字段 `roomTag`，服务端分配，恒大写**：作用域（兼职, dormKey），按绑定顺序 **A/B/C…（1→A、26→Z、27→AA）**；换宿舍重新分配；旧标签不复用；展示 `D4-522A`。
- B 继续塞进姓名/称呼后缀（v3 做法）：不稳定、会和真名混、改名即失效。
- C 全局（跨兼职）按宿舍分配：其他兼职能通过"同一个 A/B/C"推断他店顾客，违反隔离精神。
**推荐**：A。
**理由**：1) 独立字段可排序/可校验/可展示；2) 作用域按兼职保证隔离；3) 有序分配使同寝室多顾客在兼职清单里可区分；4) 换房重分配符合直觉；5) 大写与楼栋/宿舍号视觉一致（用户要求）。
**代价如实记**：1) 同一顾客换绑到另一兼职会拿到新标识（不同兼职看到的不一样，这是有意的隔离）；2) 解绑/注销留下空洞（不复用是防歧义，存储成本可忽略）；3) 极端同寝室 >26 人用 `AA` 起（正常不会）。
**被否**：B/C。
**落了什么**：CONTRACT §3/§4.2；`bindings.roomTag` + `counters` 事务 + 展示格式 + 并发/换房/重绑用例。**roomTag 与唯一编号是两套东西**：编号认人、roomTag 只在本兼职的宿舍清单里区分。**v0.9：原小写 `D4-522a` 全部作废；空库无需迁移。**

## D9 · 取件码截图的处理与留存

**背景**：v3 截图只在识别页显示，不落盘、不上传。v4 兼职需要看截图核对，且订单要跨设备。
**选项**
- **A（推荐）压缩后上传私有云存储**：长边与体积上限配置化（默认 1440 / ≤500KB）；存储私有，订单双方经云函数鉴权拿临时 URL（5 分钟）；完成/取消后 7 天自动删除；不进通知/分享/日志。
- B 不上传原图，只上传识别出的字段：顾客截图里的其他信息（如取件点位置、备注）兼职看不到，核对体验差；且顾客手填容易错。
- C 上传到公开可读路径：泄露风险，禁止。
**推荐**：A。
**理由**：1) 兼职核对取件信息需要原图；2) 私有+临时 URL+定期删除把风险压到最低；3) 压缩控制成本与上传时间。
**代价如实记**：1) 截图可能含姓名/手机号/地址，**隐私指引必须声明**，并建议顾客截图前自行遮挡（P1 自动打码）；2) 云存储成本与清理任务；3) 临时 URL 5 分钟过期可能造成"图片加载失败"，需刷新按钮。
**被否**：B（体验差）；C（安全红线）。
**落了什么**：`upload.prepare` + `upload_tickets` + 私有存储规则 + `order.imageUrl` + cleanup 引用计数删除。

## D10 · 通知方式

**推荐**：A。

## D11 · v3 历史数据是否迁移

**背景**：v3 本地 `ex_college_v3.store` 里有客户档案与包裹记录；v4 新 appid + 云数据库。
**选项**
- **A（推荐）不迁移**：v4 空库起，v3 旧小程序原样保留作参照；如个别老客户需要，手工录入。

**推荐**：A。

## D12 · 是否保留兼职"代客下单"

**背景**：第一批顾客可能还没有用小程序（比如线上只发了群二维码）；v3 的录入能力（截图识别→建单）已经打磨过。
**选项**
- **A（推荐）保留**：兼职可替未绑定顾客建单（`source=PARTNER`），之后分享绑定卡片**邀请顾客自己绑定**看进度；**代客单不产生绑定**（D20：绑定只能顾客发起）；订单在兼职工作台正常流转。
- B 只服务已绑定顾客：第一批冷启动会卡住。
**推荐**：A。
**理由**：1) 冷启动需要兼职先把线下客户带进来；2) 复用 v3 录入能力，成本低；3) 与 v4 订单模型兼容（多一个 source 字段与归属规则）。
**代价如实记**：1) 代客单的顾客资料由兼职录入，准确性由兼职负责；2) **MVP 未绑定顾客看不到代客单进度**（认领卡片列 P1），需兼职口头分享绑定卡片补充；3) 代客单与顾客单在**单量统计**上要分开口径（无收入/金额口径）；4) 代客单不带来绑定，兼职仍需顾客本人绑定后才能接其后续订单。
**落库口径**：`source='PARTNER'`、`customerId=''`、`customerOpenid=''`、`customerNo=''`、`guest{displayName,phoneTail,zone,buildingNo,room,dormKey}` 快照；**不写 `bindings`**；`claimTokenHash/claimExpiresAt/claimedAt` 仅 P1 预留。
**被否**：B（冷启动受阻）。

## D13 · 主体与类目（**提审开工门；只能用户做**）

**背景**：微信小程序"快递代取/跑腿/同城配送"类目通常需要企业主体与相应资质；个人主体可能无法选择该类目或审核不通过。v4 是真正面向外部客户的产品，不再是自用工具。
**选项**
- A 确认个人主体能上的类目（如工具/生活服务类目）并调整产品描述，避免"快递业务经营"表述；
- B 企业主体 + 相应资质（更正规，但需要注册/认证/成本）；
- C 先以体验版/内部试用（不公开发布）验证链路，上线另行裁决。
**推荐**：需要你先确认主体与类目；在确认前，开发可以照常进行（体验版/开发者工具），但**提审发布阻塞**。
**代价如实记**：若主体/类目不合规，最坏情况是产品无法公开发布；这不是代码能解决的问题，必须提前确认。另：小程序备案（2023 起）也需要主体配合。**零金钱口径（D6）有利于类目说明**：本程序不涉及支付/收费，只做信息与履约工具，提审材料按此表述。
**需要你提供**：主体类型（个人/企业）、拟选类目、是否已做小程序备案。

**落了什么**：`admin_view_sessions` 集合 + `admin.viewAsStart/viewAsEnd` + 读接口白名单 + 写拒绝 + 黄条 + 审计 + cleanup；UX 见 `docs/V4_UX_DEVELOPER.md`。**v0.9**：会话增 `viewMode/targetIsTest/targetAvatarFileId`，页面 `pkg-admin/pages/account-switch/index`（替换 view-as），蓝条/TEST 角标，`ACCOUNT_SWITCH_*` 审计，测试账号隔离与清理。

## D15 · 顾客/兼职唯一编号的样式（新增）

**背景**：用户二次修订要求"不管是顾客还是兼职人员都需要具备不同样式的唯一 id"。需要定样式：长度、前缀、分组、生成规则。
**选项**
- **A（推荐）不同前缀 + 不同长度**：顾客 `C` + 8 位（展示 `C-XXXX-XXXX`，如 `C-7K2M-9QX4`）；兼职 `P` + 6 位（展示 `P-XXX-XXX`，如 `P-7K2-M9X`）；开发者固定 `DEV-01`。字母表 32 字符（去 0/O/1/I），服务端随机生成、唯一索引、不可改、不复用。输入容错（空白/连字符/全角/大小写），前缀必填，错前缀给专门提示。
- B 纯数字短号（如 6 位）：易撞、易枚举、无法一眼区分角色，顾客号与兼职号混用风险高。
- C 中文/拼音前缀（如 `客-`、`兼-`）：输入麻烦、宽度不稳定、复制粘贴体验差。
**推荐**：A。
**理由**：1) 前缀一眼分角色（C/P/DEV），错填能立即提示；2) 长度不同进一步防混；3) 32 字符表避开易混字符；4) 随机生成防枚举，满足"顾客不能查询其他兼职"的安全要求。
**代价如实记**：1) 顾客输入兼职编号比 v3 的 6 位长（含前缀共 7 位/展示 9 字符），但支持粘贴与扫码卡片兜底；2) 编号版面占空间，列表默认不展示、详情页展示；3) 注销后编号作废不复用（随机空间足够大）。
**落了什么**：CONTRACT §3.1 编号规格 + `utils/ids.js` + 唯一索引/碰撞重试 + 错前缀提示 + 绑定/展示/后台搜索 + 验收用例。

## D16 · OCR 识别失败兜底：DeepSeek API（新增，三次修订）

**背景**：用户三次修订要求"引入 deepseek api 在 ocr 识别站点、取件码失败时作为备选，并格式化返回"。端侧 OCR（v3 阶梯）受截图质量/字体/版式影响，站点或取件码识别失败时只能手填；DeepSeek 文本模型可对 OCR 文本做结构化抽取。
**选项**
- **A（推荐）云函数调 DeepSeek**：客户端在本地规则解析失败后调 `ai.parseParcel`；服务端二次去敏，只发 OCR 文本（≤2000 字，不含原图/openid）；`deepseek-chat` + `response_format=json_object` + `temperature=0`；8s 超时、重试 1 次、熔断、限流 5 次/人/日 + 全局日配额；失败静默降级并写复核队列；返回统一 DTO（`recognized/stationId/stationName/pickupCode/trackingTail/lockerNo/confidence/source/needsReview/failureId`）；AI 只做预填建议，不覆盖用户手填。
- B 客户端直连 DeepSeek：Key 必须下发到客户端，**禁止**。
- C 不用 AI：识别失败只能手填/人工复核，体验最差（保留为兜底开关关闭时的降级路径）。
**推荐**：A。
**理由**：1) Key 只在服务端，安全；2) 文本外发可去敏、可限额、可审计；3) 失败仍走既有手填 `NEED_CODE` 机制，不阻断下单；4) 换模型/换服务商只改云函数适配层。
**代价如实记**：1) 第三方可用性与延迟（≤8s）影响体验，必须降级；2) 隐私披露与微信"第三方服务"声明必须写；3) OCR 完全无文本时 AI 也帮不上，直接进复核队列；4) DeepSeek 当前无视觉 API，不能直接看原图。
**落了什么**：CONTRACT §4.3/§5.3/§11 例外与第三方披露/§14-8；DATA_MODEL `ai.parseParcel` + `recognition_failures`；UX_CUSTOMER/UX_PARTNER 兜底中间态与失败码文案；ENGINEERING 云函数适配层 + check.js 门禁 **#24~#27**（v0.9 后新增 #28~#31）。

## D19 · 微信头像与昵称采集（新增，四次修订）

**背景**：用户四次修订要求"无论是顾客还是兼职人员，均需要获取其微信头像与微信名称，顾客应该能看到其绑定的兼职人员的微信头像、昵称；兼职人员的用户档案内能看到对应的头像和昵称"。
**选项**
- **A（推荐）平台标准采集**：`open-type="chooseAvatar"` 取微信头像 + `input type="nickname"`（可一键填入微信昵称）；昵称**必填**、可改/手填、≤20 字超长截断、过 `msgSecCheck`；头像**可拒绝**→默认头像（首字色块），不阻断下单/接单；头像存云存储 `avatars/{role}/{random}.jpg`（**不含 openid**）、≤200KB、替换删旧、注销删文件；**仅当前 ACTIVE 绑定的对方可见**（顾客见绑定兼职、兼职客户档案见绑定顾客），解绑后不再返回；**绑定前预览只回昵称、不回头像**；后台列表**不展示头像**、昵称脱敏；分享卡片/通知不含；代客单 guest 用默认头像；已缓存副本无法技术撤回（隐私文本写明）。
- B 强制获取且不可改：违反微信"用户主动选择"原则，且用户可能拒绝授权导致流程卡死，**不做**。
- C 只采集昵称不采集头像：不满足用户"均需获取头像与昵称"，**不做**。
**推荐**：A。
**理由**：1) 用微信官方能力，合规且无需自建头像审核；2) 拒绝降级保证流程可用；3) 可见范围最小化（仅绑定对方），后台与卡片不扩散；4) 字段挂在角色资料上，与 `displayName` 既有口径兼容。
**代价如实记**：1) 微信后台隐私声明必须新增"头像/昵称"，隐私指引与发布前清单要同步（不提审会被驳回）；2) 头像文件带来存储/清理与缓存一致性成本；3) 昵称从可选变必填，激活/资料页流程要加一步；4) 拒绝头像的用户显示默认头像（视觉不统一）。
**落点**：CONTRACT §3/§4.1/§4.2/§5.3/§8/§10/§11/§12 门禁 #29；DATA_MODEL customers/partners/upload_tickets；UX_CUSTOMER 资料页/我的/绑定确认/订单详情；UX_PARTNER 激活/我的/客户档案；ENGINEERING privacy.js/头像上传/门禁；QA 与 privacy 两件。
**被否**：B/C。

## D20 · 绑定方向：只能顾客绑定兼职（已定，四次修订）

**背景**：用户四次修订要求"兼职人员只能被顾客绑定，无法绑定顾客"。
**结论（已定）**：**绑定只能由顾客发起**——顾客凭完整 `partnerNo` 或卡片落地调 `bind.create`；`bind.create` 仅 CUSTOMER 业务角色可调，PARTNER 调用 `FORBIDDEN`；兼职端**不得出现**添加/绑定/导入顾客的任何入口；代客下单**不产生绑定**；兼职只能 `unbindCustomer`（原因必填 + 通知）；解绑后双方不再互见头像/昵称；测试账号只能与测试账号互绑。
**理由**：1) 绑定是顾客主动授权"谁能看到我的宿舍/订单"，方向必须由顾客掌握；2) 兼职主动绑定 = 越权获取他人信息与抢客/骚扰风险；3) 与 v3 单人台账"自己录顾客"彻底切割，避免旧模型回潮。
**代价**：兼职无法主动拉客，只能分享绑定卡片邀请顾客自己绑定；没有 app 的顾客只能走代客单（不绑定、看不到进度）。
**落点**：CONTRACT §1/§2 D4/D12/§4.2 铁律/§10/§12 门禁 #28；DATA_MODEL bindings/动作/负向；UX_PARTNER 全页删除绑定入口；UX_CUSTOMER 绑定入口唯一；QA 负向；ENGINEERING 角色中间件。

## D22 · 截图上传失败后是否允许「无截图手填提交」（批 4 实现期登记，待裁）

**背景**：批 4 端侧收口时发现文档张力——`V4_UX_CUSTOMER.md` §4.5 原则句写「「手输必须能存」底线保留：OCR/上传失败都可手填提交」；但 §4.2/§10 的上传失败错误表只给「重试」，下单页当前要求先有截图（`image/ticket` 必填）才能提交。服务端 `orders.image` 字段为可选（DATA_MODEL §2.5），核验逻辑允许无图建单。
**选项**：
- **A（推荐，现状）**：保持「必须先有截图才能提交」——上传失败只能重试/换图；OCR 失败（截图已上传成功）仍可手填提交 `NEED_CODE`。理由：兼职无图难以核对、防误单；与 §4.2/§10 错误表一致。
- **B**：允许上传失败后无截图手填提交（`orders.image=null`，`NEED_CODE` 可提交）。更贴合"手输必须能存"底线，但兼职端无图核对、复核队列无原图可看（TD-019 同类降级）。
**裁决影响**：选 B 需放开页面 1 行校验（`onSubmit` 的 image/ticket 检查）+ `selftest-order-flow` 补断言；选 A 需把 UX §4.5 原则句限定为「OCR/阅读失败可手填，上传失败须重试」并回写 UX/QA；当前按 A 实现，未做单方面产品变更。
**落点**：CONTRACT §4.2/§4.5/§10/D22；UX_CUSTOMER §4.2/§4.5/§10；DATA_MODEL §2.5 `orders.image`；QA D3/D9/D12；`STATE.md` §4 #13 与 `TECH_DEBT` TD-039。
