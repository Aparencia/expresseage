# 2026-10-22 · 计数器首次取号只预留 1 个 → 当天后续下单全挂

- 现象：当天**首单是一图多码拆单**（`order.createBatch` 一次取 N 个 `orderNo`）时，当天后续每一次下单都返回 `INTERNAL_ERROR`；客户端只看到「操作失败，请重试」。
- 根因：`lib/id-generator.nextOrderNos` 首次取号分支把计数器落成 `{seq:1}`（只预留 1 个），但已返回 `0001..000N`；同日下一次取号从 `1+1=2` 起，撞上已用的 `orderNo` → 唯一索引冲突 → `_create` 的 duplicate 分支按 requestKey 查不到 → 原样上抛 `INTERNAL_ERROR`。
- 为何长期未发现：历史断言只覆盖「单号+重复单+状态矩阵」，没有任何判据走「当天先拆单、再下一单」的取号序列；`selftest-cloud` 全绿也不代表计数器语义对。
- 证据：cross-domain 探针首红——修复前 `orderNos=["…0001","…0002","…0003"]` 但 `counters.seq=1`，随后 `order.create → INTERNAL_ERROR`；修后 `seq=3`、第二单 `ok=true` 且 `orderNo=…0004`。回归断言常驻 `tools/selftest-order.js` D5b/D5c。
- 教训：①**计数器/取号类原语必须按「预占 N 个」写游标**，返回列表与游标必须同源；②序列型判据要覆盖「批量后接单件」这种跨调用时间顺序，不能只测单次；③跨域 1 行修复也必须配真实回归断言（防再次退化），不能只留一句注释。
- 落地：`{key, seq: total}` 一行修复（Lead 授权跨域）；`selftest-order` 126 断言含取号序列正控。
