## 3. SWOT（每格 1~3 条，均可验证）
- S：用户就是本校学生团队，沟通零成本；只做信息整理与排序、不碰支付与资质（绕开"个人主体不能开微信支付"，见 §5.3）
- W：单人 + 碎片时间 4 周 ≈ 28~56 小时（用户答）；小程序"备案+审核"是硬门禁——2023-09-01 起未备案不得上架（来源：光明网转微信公众平台通知 https://m.gmw.cn/2023-08/12/content_1303477786.htm）
- O：现存方案是"群+表格"，其痛点已被同行内容页写明（见 §1）；高校快件占比 8% 说明需求密度稳定；"按站点聚合"是现有表格做不到的差异点（来自六问③）
- T：校园跑腿 SaaS 若低价/免费进校＝降维打击；校方对"校内代取"的管理态度未知（无来源）

## 4. MVP 最薄切片（4 周内给真人用；因六问③ 已重切一次）
- **重切理由**：六问③ 的回答把痛点从"记账乱"改成"站点分散→同一趟反复回到去过的站点"——核心价值不是台账，而是**按站点聚合、一趟取完**。
- 做出来的是什么：只在队长+兼职小圈子里用的微信小程序——兼职端按**站点分组**看"本站点待取 N 件（客户 A/B/C）"、取完一站勾掉一站；队长端"今日总览（谁在跑、每站剩几件、未送达清单）+ 按人汇总单数与金额 + 复制结算文本发群"。
- 首个用户怎么用：队长把小程序码发进团队群 → 兼职点开看到站点分组 → 按站点顺序取件、逐站勾掉 → 送达后按客户标记 → 队长看汇总 → 复制结算文本发回群里。
- 明确排除：不做支付提现、不做学生端下单、**不做地图路径规划**（只按站点去重排序，不写算法）、不做自动派单、不做多校区、不做订阅消息推送。
- ⚠️ 备案与审核时长未查到公开数据 → 4 周内必须预留时间；必要时降级为"队长一人录入"先验证流程。

## 5. ⚠️ 待验证直觉（不是证据，不参与判分）
1. 兼职愿意打开小程序点两下、而不是在群里回一句"我拿走了"——最小实验：先用在线表格跑 3 天，看到达率。
2. 队长愿意为省掉每天约 20 分钟对账而持续用——最小实验：手工帮他做 3 天结算表，问是否愿意换成小程序。
3. 个人主体小程序够用（不开支付）——二手整理称个人主体不支持微信支付、部分类目受限（来源：https://www.uweb.net.cn/zhishiku/jianzhanliuchengyugongju/32890.html ⚠️ 第三方整理、非官方，需以微信官方文档复核）
4. 同一趟真能合并出足够多的单——最小实验：让他把某一天的全部订单手工按站点分类，数出"可合并/总单数"比例；低于 30% 则本切片的核心价值不成立。
