# DECISION_2026-09-19 · 整站取完的批量写接口（expresseage_college）

> 裁决日 2026-09-19｜依据：`docs/reviews/CODE_20260919_station_library.md` R-04（P2）+ R-10｜修复批 SCOPE `M5` / `M15`
> 被触发的既有决策：站点库任务（2026-09-17）曾定「**不新增批量 API**，改数据只保留一条路径」（`docs/registry/COMPONENTS.md` 的"整站取完"行）

## 选了什么

在 `utils/storage.js` 内新增 **`setParcelsStatus(ids, status)`**：一次全库读 → 内存改 N 条 → **一次整键写**。

- 语义仍是"改状态"，且仍只有存储层碰 `wx.*Storage*`（`tools/check.js` 第 6 条分层判据不变）
- **要么全部改成功、要么一条都不改**：先整体预校验，任一 id 不存在/已删除 → 不写盘
- 失败时把 `missing:[id]` 回报给页面（用户要知道是**哪几条**没改成，而不是只看到一个数字）
- 页面侧 `pages/pickup-list/index.js` 的「整站取完」改调它，不再 `for` 循环逐条调 `setParcelStatus`

## 为什么推翻原取舍

原取舍的**目标**是对的（改数据只保留一条路径，便于审计与回滚），但它的**实现方式**把"一次用户动作"变成了 N 次独立写：

1. N 次全库读 + N 次整键写 —— 写放大（R-10）
2. 中途失败留**半完成态**；而确认框向用户承诺的是"该站 N 条将标为已送达"（R-04，违反 24 卡 §②维度 2「禁止半完成状态」）
3. 失败只回报条数，不回报**哪几条**

批量入口把"一条路径"从**函数级**收敛到**层（模块）级**：改数据仍然只经过 `utils/storage.js`，而原子性反而更强。

## 被否方案与否决理由

| 方案 | 否决理由 |
| :-- | :-- |
| 保持逐条调用，只改"回报哪几条" | 半完成态仍在、N 次写放大仍在，确认框的承诺仍不成立 |
| 页面侧先 `listParcels`、改完再一次写盘 | 页面会绕过存储层直接碰存储 → 违反分层判据（`tools/check.js` 第 6 条会拦） |
| 新增一套"批量"错误码 | 不需要：复用 `NOT_FOUND` + `detail=PARCEL_BATCH_MISSING`，避免码表膨胀 |

## 已知风险与未决项

- **没有事务日志**：本地存储是整键覆盖，"一次整键写"就是本项目能拿到的最强原子性（无 WAL、无回滚段）。要更强需换存储层 → 属重裁 `STACK_2026-09-15_微信小程序.md`。
- `missing` 只覆盖"不存在/已删除"这一类；**写盘失败**（配额/IO）时整体不写，页面按 `reasonText` 提示，不区分具体是哪几条 —— 因为那时一条也没改。
- 与 `storage.archiveDoneParcels()` 的"无事可做就不写盘"约定一致：批量接口在 `ids` 为空时直接 `VALIDATION_FAILED`，不做空跑写盘。
