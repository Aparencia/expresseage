## 3. 根因（五问法，逐层到底）

1. **为什么识别完成后表单什么都没填、还弹"识别流程异常"？**
   → `applyParse` 调用的 `planParsePatch` **抛了异常**；异常被 `pages/recognize/index.js:322-324` 的 `.catch` 接住，转成那句 banner。⇒ 屏上"什么都没发生"其实是"崩在了 catch 里"。
2. **为什么 `parse` 未定义？**
   → `pages/recognize/form-parts.js` 顶部只 require 了 `aggregate`(12) / `parcelDrafts`(13) / `stations`(17) / `intake`(420)，而第 **450/456** 行直接写了 `parse.parseParcelTextMulti(...)` / `parse.parseParcelText(...)`；第 **464** 行用了 `reasonText(...)`，同样没有绑定（该文件顶部注释第 14-16 行还写着"`reason.js` 本文件不再 require"——**注释是搬家的证据**）。
3. **为什么一个没有 `parse` 的文件里会用到 `parse`？**
   → 因为这段代码**原来住在页面里**（页面当时 require 了 `parse` 与 `reason`），提交 `23eb527` 为守 500 行硬线**整簇搬进零件**，搬迁只搬了函数体 ⇒ **依赖没跟着走**。三条硬证据（取数命令见 §8）：
   - `git show 23eb527:pages/recognize/form-parts.js | Select-String "require\('\.\./\.\./utils/(parse|reason)"` ⇒ **零命中**：搬进来的那一刻就没有这两个绑定；
   - `pages/recognize/form-parts.js:14-16` 的注释写着「`reason.js`（失败文案单源）原先只被 ② 内联新建那一簇用到 ⇒ 随它一起搬去 `./create-parts.js`，**本文件不再 require**」——这句"不再 require"正是漏掉 `reasonText` 的认知来源；
   - 而 `./pages/recognize/create-parts.js` **从来没有存在过**：`git log --all --diff-filter=A -- pages/recognize/create-parts.js` 零命中；`reasonText` 实际是 `index.js:16` 与 `intake-parts.js:20` 各自 require 的。
   ⇒ 搬迁时的自述（"随它一起搬去 create-parts.js"）**本身就不成立**，没人复核这句话 —— 与教训卡 `2026-09-25_自述范围大于diff.md` 同形（自述与 diff 不符）。
4. **为什么搬迁漏依赖没有任何闸拦得住？**
   → ① `tools/check.js` 的语法档（`node --check`）只查**语法**——自由标识符在语法上完全合法；② `tools/selftest.js` **从没调用过 `planParsePatch`**：全仓 `grep -rn "planParsePatch"` 只命中 `STATE.md` / `pages/recognize/index.js` / `form-parts.js` 自身 / `docs/registry/APIS.md` / `docs/specs/.../FIX2.md`，**没有一行断言**。⇒ 683 条断言对它 **0 条覆盖**，两道门禁全绿（`check.js` 50/50、`selftest` 683/683 —— 取数命令见 §8）而功能 100% 死 = 教训卡 `2026-09-19_空集上的全绿.md` 的同族。
5. **为什么"搬出来就是为了可断言"这句话没兑现？**
   → 搬迁把**可测性的前提**做到了（纯函数 + 导出 + 页面只转发），但**断言是下一张卡的待办**。同一批在 `selftest-wave6.js` 里写了 §13/§14 几十条断言，**唯独漏了这个新 export** ⇒ "搬出来"与"配上断言"被当成了两件事，而**中间那一刻它就是一段没人跑过的代码**（同族：`2026-09-19_只在新装机或真升级路径上炸.md`）。
6. **更深一层（真正的根因）**
   → 项目的"覆盖面"是**按人挑的函数**长的，没有任何东西要求"新增/搬出的每个 export 至少被跑过一次"；也**没有任何判据能看见"模块引用了不存在的名字"** ⇒ 覆盖面缺口与代码缺口一样**无声**。维修法只能是"人记得补"，而这一批恰好没记得。

## 4. 附带缺陷（同族，本轮一并登记 —— 真机形态未证的两条已标注）

### 4.1 缺陷 B（一图多码把"脱敏手机号末四位"当成取件码）⚠️ 转录样本实测，真机未证

转录样本（图3）喂进多码路径后，**1 件被报成 2 件**（探针场景 ②/③）：

```
图3 韵达·菜鸟：ok=true 条数=2  → [111-1-1111 @ 湖工大西苑一栋南面菜鸟驿站] [<该行末四位> @ ❓]
```

链路（四层）：

1. 一图多码的 `collectCodeHits` 把"**带标签的码**"与"**无标签的码**"**求并集**（用户 2026-09-19 裁决 R-05：宁可多一行让人删，也不静默漏件）；
2. 无标签那半会走 `parse.js:468` 的 `trailingDigitRun`（**行末 4~6 位数字**）；
3. 收件人行在真机截图上手机号是**平台脱敏后的形态**（`86-138****xxxx`），而 `NOISE_PATTERNS:57` 的电话过滤只认**完整 11 位**（`/(^|[^\d-])1\d{10}([^\d-]|$)/`）⇒ 该行**不算噪声**；
4. `trailingDigitRun` 的否定环视只看"前一位是不是数字/`-`/`_`/`#`"，**脱敏符 `*` 不在其列** ⇒ 末四位被当"行尾纯数字码"收走，`isCodeLength(x, false)`（4 位 ≤ 6）再放行。
   ⇒ 单条路径被"带标签优先、命中即返回"挡住了（`collectCodeCandidates:512-513`），**只有一图多码这条路易感**。

影响：多出一条**错码**草稿（站点 ❓）；点「全部保存」会把错码写进库 —— 正是本项目最贵的那类错（拿别人的码去驿站）。
⚠️ 诚实边界：**"VisionKit 会不会这样吐这一行"未证**（转录样本 ≠ 真机输出）；但 `*` 之后不是取件码这一点与形态无关。
⚠️ **2026-09-26 真机原文到手后本条降级为 TD-032**（依据消失）：真机那种"整屏一整行"的形态下该假件**不出现**，且 `*` 在 `cleanLine` 阶段就已换成空格 ⇒ 原建议的 `*` 判据是死代码。结论与翻案条件见 `FIX.md §9.1/§9.5` —— 本次如实记：**这条是"转录样本"自己造出来的缺陷**。

### 4.2 缺陷 C（banner 与站点提示互相打脸 —— 2026-09-25 真机缺陷的同族再现）✅ 机制与转录无关

图1 实测：卡片**为空的站点格** + `banner = 已自动填好，请核对后保存（每一格都能改）。` + `stationHint = ⚠ 站点没认出来 —— …` **同时上屏**（探针场景 ①，图1 那段）。
机制：`parsed.ok` 判的是**解析层找没找到站名**（`五食堂21栋楼下` 也算"找到"），而站点格只接受**取件点正式名**（`stationPrefill` 命不中一律留空，2026-09-25 裁决）⇒ **两个判据不同源**。
2026-09-25 修的是"格子已填好却说没认出来"，这次是**反方向**：格子空着却说"已自动填好"。

### 4.3 缺陷 D（站点清单里没有图1 那个点）✅ 已定位，属清单口径

图1 的站点是 `兔喜快递超市代收点 | 五食堂21栋楼下` ⇒ 解析层取到 `五食堂21栋楼下`，但它**不在** `STATION_POINTS`（P1~P7）、`STATION_ALIASES` 也没有对应形态 ⇒ `stationPrefill` 恒空（= TD-025 的形态，那次是 `湖工大西苑一栋南面菜鸟驿站`）。
⚠️ 加不加取件点、正式名怎么取，属**清单口径**（AGENTS §4 / TD-025 先例：agent 不擅自加数据、不擅自定名）。

### 4.4 图2 的 `NO_TEXT`：**没有根因，需要真机读数**（不许猜）

`NO_TEXT` 的判据是"首个文字到达前等了 `MAX_WAIT_MS = 3000ms` 一个字都没来"（`utils/ocr.js:17,96`）。09:00 那次一条没来、09:01 那次来了 ⇒ **更像偶发/超时**，但真机两轮读数不足以定因。
⇒ 不进 §7 批 1；**先要真机读数**（同一张图连试 3 次：稳定失败还是偶发？），再决定要不要动 `MAX_WAIT_MS` / 加重试。⛔ 不凭"看起来像超时"去调参数（教训卡 `2026-09-17_没有样本就不扩规则.md`）。

## 5. 影响面

- **识别整条动线 100% 失效**（所有"识别出字"的路径都崩在 `parse`）⇒ 用户侧观感就是"这功能只能手填"，而手填路径本身是好的（M6 未破）。

- 取件点清单缺口（缺陷 D）只影响不在 P1~P7 的站点 ⇒ 表现是"站点留空 + 明说"（降级正确，不是错值）。
- 数据面：无数据丢失、无越权、无网络请求；已存库的既有记录不受影响。
