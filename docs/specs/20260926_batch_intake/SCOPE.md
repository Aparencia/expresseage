# SCOPE · 一次性多选多录入（2026-09-26 · 用户诉求 #2）

> 用户原话（逐字）：「**2、新增一次性多选多录入能力**」
> 形态裁决（逐字）：「**A 但要有单条保存入口**」——A = 串行批量 + 共用一屏多码列表
> 起点锚点 = `62e5ab4`（本批开工时 `git rev-parse HEAD` 取数）｜档位 **L**（动取图入口 + 识别流水线 + 保存路径）
> ⚠️ **本件是对既有裁决的反转**：`docs/specs/20260923_chat_pick/DESIGN.md §5` 明写「多张串行流水线（v1 的
> `utils/pickqueue.js`）**判为不搬**」，理由是"一次只处理一张、降级口径只有一条"。用户本次诉求**取代**该裁决。

## 1. Must（必须做到）

| # | 条目 | 判据 |
| :-- | :-- | :-- |
| M1 | 两个取图入口都支持**一次多选**（`chooseMedia` 的 `count` > 1；`chooseMessageFile` 同） | 真机点一次能选中 ≥2 张 |
| M2 | 选中的 N 张**逐张串行识别**（复用 `utils/ocr.js` 的串行队列，绝不并发 —— VKSession 页面单例） | 代码路径只有一条队列；无并发调用 |
| M3 | 识别结果**汇总到同一屏**多码列表（现有 `drafts` 列表），每张图的件都进得去、不互相覆盖 | N 张图的件数之和 == 列表条数 |
| M4 | **单条保存入口**（用户补充要求）：列表每行可以**单独存**，不必等"全部保存" | 真机点某行「存这条」⇒ 只落这一条、其余留在屏上 |
| M5 | 一键「全部保存」仍是**原子**的（要么全进要么不进，现有 `commitDraftsSave`） | 现有 §M 断言不倒退 |
| M6 | 每张图的**识别原文**都能展开查看（逐张并列，标清来自第几张） | 屏上可核对，不混成一段 |
| M7 | 任一张识别失败**不阻断**其余（失败那张如实说明，其余照常进列表） | 一张 `NO_TEXT` 时其余 N-1 张仍进列表 |

## 2. Won't（本次明确不做）

| # | 不做 | 理由 |
| :-- | :-- | :-- |
| W1 | 不做"一次选中后**自动**落库" | 认错码的代价高（拿别人的码去驿站）；核对必须由人做 |
| W2 | 不做跨客户自动分堆 | 归属在**保存时**裁决（2026-09-25 裁决未被取代） |
| W3 | 不做断点续传/后台任务 | 无后端、页面一退即停；"识别到一半退出去"按现状处理（重来一次） |
| W4 | 不新增任何存储键/字段 | 数据形态不变（`parcel-drafts` 的 `key` 只在本页内存用） |

## 3. 验收（真机逐条点）

| # | 验收 | 判据 |
| :-- | :-- | :-- |
| V1 | 一次选 3 张图 ⇒ 三张都识别、件数与屏上条数一致 | 目视计数 |
| V2 | 其中一张是"整屏一行"的客户截图 ⇒ 该张的结果按现有规则走（可能只有站点/尾号） | 与单张行为一致 |
| V3 | 点某一行「存这条」⇒ 只落一条、列表少一行、其余保留 | 取件清单里可见 |
| V4 | 再点「全部保存」⇒ 剩余行一次落库，原子 | 清单里可见；无半完成态 |
| V5 | 三张里有 1 张 `NO_TEXT` ⇒ 其余两张照常进列表，失败那张有一句如实说明 | 屏上文案 |
| V6 | 换客户后保存 ⇒ 归属按"手选 > 会话键唯一命中 > 当场建档"三级裁决（不被本批改动） | 现有 §14 断言不倒退 |

## 4. 风险与必须钉住的点

1. **列表行的 `key` 冲突**：N 张图各自从 `d0` 开始编号 ⇒ 汇总时必须重新编号（否则后一张覆盖前一张）。
   → 断言：两张图各 1 件 ⇒ 列表 2 行、key 不重复。
2. **`customerId` 绑定时机**：多张图识别时客户可能还没选 ⇒ 行上先留空，保存时统一裁决（W2）。
3. **串行队列的等待时间**：N 张 × 每张最多 8s（`MAX_WAIT_MS`）⇒ 必须有**进度显示**（"第 2/3 张…"），
   否则用户以为卡死。→ 验收 V1 里一并看。
4. **反转既有裁决要留痕**：`DESIGN §5` 的反转必须写进本件的 §0 与 `CHANGELOG`，⛔ 不许静默覆盖。
