## 1. A/B：内联建档改成"一次输入就够"（按用户构想）

用户原话：「A、B与我的构想有出入」「我构想中没有用户档案时，由于大概率使用了从聊天选图，所以可以获得会话键，因而只需要求输入类似 d3455 就能够完成建档与快递码录入」

根因（两条，都出在"只做了一半"）：

1. `createCustomerDraft` 把 `chatRoomId` **硬编码成 `''`**（旧注释还写着"内联新建不碰会话键"）⇒ 就算拿得到键也不绑；
2. `onCreateSubmit` **只建档、不落件** ⇒ 建完还得再点一次「保存」；与"一次输入完成两件事"差的就是这一步。

修法：

- `createCustomerDraft(customers, line, sessionKey)`：键**有则绑、无则为空**，⛔ **绝不阻塞建档**（平台只在聊天工具模式下给明文 id，拿不到键是常态）；只接**摘要槽**（`chatKey`，不可逆、非平台原文），平台原值槽一律不由本路取（那条槽的一次性令牌与 `fromChatFlow` 闸门仍只归档案页动线）。
- `submitCreateCustomer(line, {storage, sessionKey, draft, drafts, recognitionUsed})` + `savePendingFor(...)`：**先建档、后落件**（件必须挂新档案名下）；多码走 `addParcels` 一次整批写；**存件失败不回滚建档** —— 把失败摊开说，而不是把已经建好的档案悄悄删掉（那才是删数据）。
- `createSubmitPatch(result, label)`：提交后要写的 data **不含任何 `draft.*` / `drafts` / `lines`** —— 这是"已填内容丢不了"的**结构**证据（与开浮层同一把闸）；**两件事都办完才退屏**。
- 页面 `onCreateSubmit` 只转发（页面层零断言 TD-016 ⇒ 判据必须住在零件里）。
- 入口面（B）：清单页的 `list-parts.intakeTarget` 上一批已放行"零档案"；本批补的是**进去之后真能建、建完真能录**。
- 输入形态**照旧复用单一值域闸**（`utils/customer-input.buildCustomerInput`）：实测 `d4555` ⇒ `building=D4 / dorm=555 / name=D4 555 A`（自动补名），⛔ 本页零正则、不新增语法。

## 2. D：删除后立即刷新

用户原话：「优化在删除后立即刷新」

根因：四条路径（软删 / 恢复 / 逐条彻底删除 / 全部彻底删除）里**三条只刷新了档案列表**，底部「已删除(N)」入口的**计数与件数合计**要等下一次 `onShow` 才更新；而这一页**没有任何页面级断言**（TD-016）⇒ 少写一个键谁都看不见。
