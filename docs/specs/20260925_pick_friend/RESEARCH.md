**三处官方文本互证（都能回指原文，不是我的推断）**：

| 出处 | 原文口径 |
| :-- | :-- |
| `wx.getChatToolInfo` API 页 | success 回调**只有** `errMsg` / `encryptedData` / `iv` / `cloudID`；明文字段只出现在"敏感数据有两种获取方式…**获取得到的开放数据**为以下 json 结构"那一段 |
| `wx.getGroupEnterInfo` API 页 | **同样只有** `errMsg` / `encryptedData` / `iv` / `cloudID`；明文同样在"解密得到的开放数据"段。其参数 `allowSingleChat`（返回 `open_single_roomid`）、`needGroupOpenID`（返回 `group_openid`）说明**字段名是官方定的，但出口仍是加密** ⇒ 换接口不能绕过 |
| 《聊天工具模式开发指南》§3.1 | 列三种 id（`opengid` / `open_single_roomid` / `group_openid`）与两个接口的分工：**进入前**用 `getGroupEnterInfo`、**进入后**用 `getChatToolInfo` |

**结论（分两层说，别混）**：
1. **"唯一"**：文档层面**没有第二条款式**（不存在"明文返回"的平行描述）⇒ 按当前官方口径，加密是唯一出口。
2. **"稳定"**：我给不出"永远不变"的证明。手上是**2025-05-10 的文档快照 + 两个 API 页的同一口径**；本次取官方 live 页正文**被导航截断**（只拿到 404 壳与目录）⇒ 这条只能算"当前口径"，不算"已验证"。
3. **但"加密 ≠ 死路"**：官方留了一条**免自建后端**的旁路 —— `cloudID`（**开通云开发**的小程序才返回）可通过**云调用**直接取开放数据。所以精确结论是：**要么有 session_key（自建后端），要么有云开发**；两条对本项目都是**新依赖**（v2 的立案前提恰恰是"无后端、无云、零依赖"）。

**同一轮顺手用官方原文钉死的两条（都是利好，直接影响方案 A）**：

- **U-2 有官方支点（从"未取证"升为"官方明列"）**：指南 §2.1 原文——「**当小程序处于普通模式时**，开发者调用 `wx.openChatTool` 但不传入聊天室 id，微信会拉起聊天列表让用户选择，用户选择后绑定聊天室进入聊天工具模式」。这正是用户要的"新建时自动进入选择聊天好友"；官方只限定 `url` 参数必须是**聊天工具分包内**的页面路径。⛔ 仍需真机确认调用点（主包页面）被接受。
- **U-9 关闭**：指南 §2.2 原文——退出聊天工具模式的方式之一是「在聊天工具中回到非聊天工具分包页面中（包括用户自己触发返回、开发者调用 `wx.navigateBack` / **`wx.switchTab`**）」；被禁的只有 `wx.navigateTo` / `wx.redirectTo`（须先 `navigateBack` 退出再跳）。⇒ **`switchTab` 官方允许**，代价是**退出聊天工具模式**（内存桥这条设计因此本来就是对的）。U-9 只留一条真机确认。

## 2.2 标识选型（用户追问："我需要一个长期多次选择都能稳定锁定到正确好友的标识"）

**新找到的关键接口：`wx.selectGroupMembers`**（[镜像快照](https://www.bookstack.cn/read/miniprogram-202505/69755ff831e4b8a3.md)，基础库 3.7.12+）：

> 功能描述原文：「选择聊天室的成员，并返回选择成员的 `group_openid`。**若当前为群聊，则会拉起成员选择器；若当前为单聊，则直接返回双方的 `group_openid`。**」
> success 回调原文：`members` — `Array.<string>`，「所选用户在此聊天室下的唯一标识，同一个用户在不同的聊天室下id不同」。

**为什么它是本需求的解**：它是**唯一**一个把 id 以**明文字段**（`Array<string>`，**没有** `encryptedData`/`iv`）返回的聊天工具 id 接口 ⇒ **免后端、免云开发**；且**单聊下不需要用户再点一次成员选择器**。

**候选键对比（作用域 / 稳定性 / 可得性）**：

| 候选键 | 来源 | 作用域 | 稳定性 | 可得性 |
| :-- | :-- | :-- | :-- | :-- |
| `open_single_roomid` | `getChatToolInfo` / `getGroupEnterInfo` | **会话**（单聊房间）标识 | 该单聊存在期间稳定 | ⛔ 加密（需 session_key 或云开发） |
| 自己的 `group_openid` | `getChatToolInfo` | 学生**在该会话**下的标识 | room-scoped | ⛔ 加密 |
| **对方 `group_openid`** | **`wx.selectGroupMembers`（单聊直接返回双方）** | 用户**在该会话**下的标识 | room-scoped；**同一好友同一会话长期稳定** | ✅ **明文数组，免后端** |
| 本地锚：楼区 + 宿舍 + 称呼 | `createCustomer` 既有字段 | 人可读身份 | 由人维护 | ✅ 已有 |

**推荐设计（建议 A1，待用户裁决）**：
1. **主键 = 单聊返回的两个 id 排序后拼接的无序对**。单聊房间只含 {学生, 该好友} 两人 ⇒ 该无序对**唯一标识这个好友的单聊**，且**不需要区分谁是自己**（两份 id 都是 room-scoped，逐个区分反而没有依据）。
2. **副锚 = 楼区 + 宿舍 + 称呼**（既有字段，人可读）：用于人核对、也用于主键失效时的识别线索。
3. **必须带一条"重新绑定 / 合并"路径**：官方**没有任何"长期不变"的承诺**（只说"同一用户在不同聊天室下不同"），会话重建就可能换 id ⇒ 工程上把稳定性做成"平台键 + 本地锚 + 可人工重锚"，**不许**把长期正确性全押在平台键上。⚠️ 这条**不是**"先建后补"（用户已否）：重锚只用于**修复已有档案的键变更**，建档时仍是"选好友 → 带 id 回来"。
4. `getChatToolInfo`（加密通道）**降为可选补充**：若某天真能拿到明文，可用来取"自己的 id"做消歧与更精确的指纹；拿不到也不影响主键成立。

**"单个聊天好友"场景的边界（2026-09-25 用户追问，逐条回答）**：
- ✅ **能支持，而且是最简形态**：官方口径"若当前为单聊，则**直接返回双方的 `group_openid`**"、不拉起成员选择器 ⇒ **一个好友 ⇒ 一个无序对 ⇒ 一一对应**，不需要群、不需要多选。
- ⛔ **但不能靠"排除自己"来确定哪个是对方**：官方明写"同一个用户在不同的聊天室下id不同" ⇒ **"自己"在每个单聊里的 id 都不同**，所以这条通道里"哪个是好友"根本判不出来。这正是主键必须用**无序对**（两个 id 一起）的原因，而不是"两个都存着好看"。
- ⚠️ **同一好友若有第二个聊天室**（另有群、删了重加、或从别处再开一个会话）⇒ 平台会给**第二个键** ⇒ 必须靠"合并 / 重锚"收敛；因此 UI 上这条路径**不是可选装饰**，是长期正确性的一部分。
- ⚠️ **前提未验**：必须处于**聊天工具模式**（即由"选择会话"进来）才能调这条接口，且 U-11 尚无真机读数 ⇒ 探查要跟"入口"同一批做（用户已裁：探针不单独做，随新任务第一批走）。

**新增取证项**：| # | 待证 | 不通的后果 |
| :-- | :-- | :-- |
| **U-11** | `wx.selectGroupMembers` 在**单聊**下是否真的**不拉起选择器**且返回**两个**明文 id；是否要求处于聊天工具模式（API 类别 = `chatTool`）；个人主体是否开放 | 若要求选择器 ⇒ 动线多一步但可用；若返回加密或需聊天工具模式且模式进不去 ⇒ 回到 getChatToolInfo 那条（加密 ⇒ 需后端/云）|
