# 教训 · 并行写同一工作树：范围门禁会把另一个批次的文件判成"越界"
**发生**：2026-09-25 `v6_align` 批 2（Lead 写 `docs/` 新文件）与 `pick_friend` 批 2（子代理写 `utils/` `pages/` `tools/` `docs/registry/`）并行。Lead 跑 `gate.ps1` 并按"本批范围"声明 `-ScopeFiles`，门禁立刻报 **4 项 `[FAIL] 越界`** —— 被判越界的全是**子代理未提交的改动**，两边其实都没越界。
**根因**：范围判据比对的是"**工作树 vs 锚点**"，不是"某个批次"。它隐含假设"一次只有一个写者"；同树有两个活跃写者时，这条判据的语义被破坏（第二个写者的文件与"没声明"的文件长得一模一样）。而**项目本来就有规矩**：23 卡并行车道附则写明——每单元开 `git worktree`（独立目录独立分支）各自实施+提交，**"多单元直写同一工作树 = 禁止"**；本次用"文件级互斥"（不同子目录）替代，互斥本身没破，但**门禁无法表达"两个批次"**。
**规矩（v2 起生效）**
1. 并行只走 `worktree`。要图省事同树并行，就必须接受：门禁的**范围判据**与**体量判据**都只能按"并集"读。
2. 同树并行时，跑门禁要声明**两个活跃批次的并集**，并在批级知会里写明"这是并集"——否则这条读数会被误读成"有人越界了"。
3. 看到 `[FAIL] 越界` 先问一句：**这个文件属于哪个批次？** 答不出来再当红灯处理。
4. 同树并行还会让**体量**判据把两个人的改动加在一起（实测 234 行 = 我的 106 + 子代理的在制品）⇒ 暂停线（×1.5）要按并集预算，不能按单批预估。
5. **批任务的起点锚点必须开工时自取 `HEAD`**，不许用派单消息里写死的哈希：2026-09-25 批 3 就是拿 brief 里的 `6602d20` 当锚点，而 Lead 中途插了一个提交（`1fc0edc`）⇒ `[FAIL] 越界：docs/specs/…DESIGN.md`（假红，越界的是**Lead 自己的**提交）。门禁的锚点判据读的是"区间"、不是"你的批次" ⇒ 只有"本批真实前驱"才有意义；**且锚点必须与"干净工作树"配对** —— 树里若留着**别人未提交的改动**，`锚点..工作树` 会把它们一起算进来（这与 `TD-017` 的"零变更也打 GREEN"是同一支门禁的两种失真：一个把"没测"读成通过，一个把"别人的活儿"读成你的）。
**下次定位**：并行派单后第一次跑门禁，先 `git status --short` 看有几个人的改动；`[FAIL] 越界` 且文件属于另一个活跃批次 ⇒ 是读数口径问题，不是越界。
**同族**：`2026-09-25_自述范围大于diff.md`（说的范围与 diff 不符）· `2026-09-17_门禁参数串成一个.md`（判据的输入没传对）· `2026-09-11_假exit码.md`（退出码被人为改写的两种来源）。
