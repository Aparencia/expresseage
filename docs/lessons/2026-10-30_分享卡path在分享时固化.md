# 分享卡 path 在分享那一刻固化，改代码救不了旧卡

- 日期：2026-10-30 ｜ 来源：D37 修复后 2 天，真实用户仍反馈「隐私同意异常」
- 现象：D37 已把分享卡 path 改成 `launch`、门禁全绿，但真实用户点开聊天里的旧卡仍直落 `role`，没有隐私同意入口、写动作全被拒。
- 根因：分享卡 path 在**分享时**写进卡片消息，聊天里的旧卡不随小程序更新而改变；D37 只影响「之后新分享的卡」。
- 叠加：客户端改动未重新「上传」体验版前，用户侧运行的仍是旧包——代码修复 ≠ 用户可感知修复。
- 修法：非启动页直落必须有兜底闸——`role`/`customer/home` 在未同意/版本变更时经 `utils/privacy-gate` 回 `launch` 过闸（保留 `bind`/`orderNo`），同意后回原落地页。
- 判据：`selftest-core` D37-b 组（判定/参数保留/版本变更/会话跳过/页面接线）+ 变异电池 3 组首红。
- 教训：改分享/深链 path 的修复，必须把「已发出的旧卡」当第一类输入设计兜底，否则线上永远有一部分用户走旧路径。
