# 教训 · `$s.Split($p)` 在 PowerShell 里把字符串当 char[] 拆：读数能差三个数量级
**发生**：2026-09-25 `v6_align` 批 3 的抽检脚本要数"某个搜索词在文件里出现几次"，写成 `$raw.Split($p1).Count` ⇒ 得到 **5710**（它把 `$p1` 当成**字符数组**，按其中任意一个字符拆开），而期望是 **1**。同一次还埋着第二个同伴：`-split` 是**正则**、`.Split()` 是**字面量**，两者语义不同却长得像。
**根因**：.NET `String.Split` 有 `Split(char[])` 与 `Split(string[], StringSplitOptions)` 等重载，PowerShell 把**一个字符串**参数绑到了 `char[]` 上 ⇒ 变成"按每个字符拆"。
**代价**：这个数若被抄进回执或文档，就是一条**假读数** —— 而且它"看起来是程序算出来的"，最难被质疑。本项目已为此立过 `2026-09-24_散文里写实测数字.md`、`2026-09-11_数字口径与CRLF.md` 两张同族卡。
**规矩（v2 起生效）**
1. 计数一律 `[regex]::Matches($raw, [regex]::Escape($p)).Count`。
2. 真要按字面分隔符拆：`$raw -split [regex]::Escape($p)` 或 `$raw.Split([string[]]@($p), 'None')`。
3. **写入/回执之前先断言读数在合理量级**：本次正是这条拦住的——期望 1、得到 5710 ⇒ 停下查脚本，而不是照抄数字（先把仪器修好，别把仪器故障当成业务缺陷）。
**下次定位**：任何"次数/条数"比预期大 2~4 个数量级 ⇒ 先怀疑被当成 `char[]` 拆了。
