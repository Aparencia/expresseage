# 数字没有口径 / CRLF 让对拍与门禁失真
现象：两个工具数同一文件行数差几十；逐字节对拍永远不等；`git hash-object` 相等**且** `git diff` 为空却仍掩盖 EOL 差异；`git stash` 后 Vite 拒绝构建；`Get-Content` 读中文日志 GBK 吞行（"新增 6 条"实为"新增 0"）。
根因：core.autocrlf=true 下工作区与仓库行尾不同；计数口径不一——**v1 口径 = `[IO.File]::ReadAllLines($p,[Text.Encoding]::UTF8).Count`（含空行）；v2 已统一为「非空行」**（`gate.ps1` 的 ④ 用 `Get-Content -LiteralPath $f -Encoding UTF8 | Measure-Object -Line`，`TD-001` 的取数命令是**同一把尺子**）⇒ **跨项目引用数字时以「所在项目的判据」为准**；⛔ 禁**无参** `Get-Content`（PS 5.1 按 ANSI 解码 ⇒ GBK 少算可达 56 行）、禁字节 0x0A 计数。**口径必须唯一且写死在判据里**——两把尺子并存就是漂移。
修法（实测）：数字带四元组（值+口径+时点+域），声明贴命令原文；字节对拍必须先行尾归一；判提交树门禁用 `git -c core.autocrlf=false archive <commit>`；autocrlf=true 的仓库禁 `git stash`。
下次定位：对拍失败；两处数字对不上；"行数/条数"类声明。
**补记（2026-09-22，24 审查 r4 抓出）——本卡第 3 行早就写了"禁 Get-Content（GBK 少算）"，我仍连犯三次，故在此留案发形态**：
- **本批实际形态**：不是"我没读卡"，而是"**我把错误的复核命令写进了文档交给下一轮审查**"。只写 `(Get-Content <f>).Count` 是**不合格口径**（PS 5.1 无参按 ANSI 解码 ⇒ 中文注释乱码 ⇒ 行被合并 ⇒ 偏小）。实测：`utils/buildings.js` 无参 **208** / 正确 **279**；`tools/selftest.js` 无参 **1554** / 正确 **1759**。
- **为什么危险**：下一轮照文档跑得到 208，与 `gate.ps1` 的 279 不符 ⇒ **要么误判文档错、要么误判门禁错，然后去改本来正确的那个数**。这正是本批 r2/r3 连续两轮"数字对不上"的病根之一。
- **行数口径 = 解码方式 × 行尾，两者都要写死**；贴给别人的命令必须**贴完整原文**（含 `-Encoding UTF8`），或统一用**与所在项目门禁同源**的那把尺子（⚠️ **v2 修订（2026-09-25 收卡批）**：v2 门禁同源 = **非空行**，见本卡第 3 行；v1 当年那句 `[IO.File]::ReadAllLines(...)` 是 v1 的尺子）。本批另核：磁盘上是 279 个裸 LF、0 个 CR ⇒ 该处**不是**行尾问题。
- **元教训**："写数字会漂、所以改写成给命令"是对的方向，但**给命令只解决了一半——命令本身也得是对的口径**。否则漂移只是从"数字过期"换成"命令算错"。
