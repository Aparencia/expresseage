# 研究：小程序能否用手机号等信息直接读取快递件信息（2026-11-02）

> **性质**：可行性研究（只读，未改代码/口径）。对应 2026-11-02 用户第 3 条需求。
> **结论先行**：**受限可行 → 对本项目不可行**。一句话：「用户手机号 → 直接读出其待取件列表」在**个人主体 + 工具类目（D13）+ 客户端零密钥/外呼只走云函数**的约束下没有合法可落地路径；小程序能拿到的「手机号」本身也不含任何快递数据，而外部快递/驿站开放平台没有面向第三方的「按手机号查件」自助接口。
> **口径源**：`docs/contract/V4_CONTRACT.md` §0（零金额）/§11（隐私：永不收集完整手机号）/D13；`docs/engineering/V4_ENGINEERING.md`（客户端零外呼/零密钥）。
> **取证**：微信官方文档 `.md` 纯文本变体 + 一手产品页（URL 见 §5）；未拿到官方依据的明确标注。

## 2. 逐项要点

1. **手机号组件只给号码，不给快递**：即使非个人主体能用，拿到的也只是用户本人手机号；要再查件仍需快递/驿站接口，而后者无公开自助接入。
2. **微信物流能力均绑定「本小程序自有购物订单」**：本程序零交易（D6/D30）、不发货，准入与场景都不适用。
3. **第三方聚合平台以运单号驱动**：没有「手机号 → 待取件列表」的公开接口；且用手机号查他人快递属处理他人个人信息，需要单独同意与合法性基础。
4. **短信无法读取**：小程序平台没有短信/通知读取能力，无法从取件短信自动取码。
5. **剪贴板是唯一可用的「用户主动提供文本」通道**：必须在用户主动触发时读取并声明隐私，且只应做端侧解析、原文不上传。

## 3. 对本项目的建议

**P0（MVP，维持现状，不改代码）**：截图 OCR + 规则解析 + 云函数 DeepSeek 文本兜底（仅去敏文本、不发原图）+ 无截图手填（D24）+ 本机取件码清单（D57）。这是唯一「个人主体可自助、零外部资质、零客户端外呼」的路径。

**P1（可选，低成本、可验收）**：「粘贴取件短信/通知文本 → 端侧规则解析」。
- 入口：下单第 1 步与本机取件码页各加「粘贴文本」输入框（用户自己粘贴，不调剪贴板 API）。
- 实现：复用端侧规则解析纯件；**端侧先掩码**完整手机号/身份证/门户等长数字，只提取站点/取件码/运单尾号；原文不落库、不上传、不进日志。
- 风险：误识别（用真机语料补 `selftest-recognize` 断言）；剪贴板隐私口径与 §11.2/§11.3 对齐。

**P2/不做**：线下与校园驿站/校方签数据合作（需企业主体或校方背书）；申请手机号组件；接入任何「按手机号查件」API；读取短信/通知；为查件升级企业主体；提审材料出现「快递查询/物流查询」类表述（避免触发类目资质审查，维持 D13「信息与履约工具」表述）。

## 4. 口径影响

1. **「永不收集完整手机号」（§11.1）不需要修改**。若 P1 上线，只补一句：含完整手机号的文本在端侧即掩码，原文不落库/不上传（与剪贴板边界同源）。
2. **零金额口径不受影响**：第三方接口计费、微信组件计费均属运营成本，不进入程序任何字段/文案/展示，也不构成程序内交易；若将来采购，只在 ENGINEERING/TECH_DEBT 记运营成本。
3. §11.2 后台填报「手机号为个人主体不可用、不勾」已被官方文档证实，可直接作为提审依据。
