# 研究：校园墙与外卖代取的可行性与角色模型优化（2026-11-14）

> **性质**：可行性研究（只读，未改代码/口径；不作为验收证据）。对应 2026-11-14 用户需求：「校园墙能力 + 外卖代取能力；一个人最多 5 个小程序、新备案很慢；当前备案能否直接支持；必须优化直接区分顾客与兼职的形式」。
> **结论先行**：**当前「个人主体 + 工具类目」不能合规地直接加入校园墙，也不能合规地直接加入外卖代取**。校园墙卡在「社交-社区/论坛」不对个人主体开放；外卖代取卡在「生活服务-跑腿/外送」不对个人主体开放。**备案已完成只说明这个主体已履行备案手续，不改变主体可选的类目范围**。两项都做的最小合规路径是：**把现有小程序主体升级为非个人主体（个体工商户/企业）+ 增加类目 + 变更/重做备案 + 补齐 UGC/外卖运营合规**；建议**先外卖、后校园墙**，分阶段过 gate。
> **补充（2026-11-16 用户澄清）**：用户场景是「外卖员已把餐送到大学东门，顾客再委托从东门取到校内」——**没有商家/餐品选择、没有站内下单、没有公开抢单**。这个形态记为 **E 校门代取已送达物品**。**E 与现有快递代取同形态**（已到达物品 + 绑定/指派 + 取送），不是外卖平台/点餐平台；**备案上不新增服务类型**，但备案描述若只写「快递」，建议补充/变更为「校园物品代取（快递/外卖等已送达物品）信息与履约工具」；**微信个人类目仍没有跑腿**，「外卖」字样会提高审核联想，保持与快递完全同形态可把风险降到与现有快递相同，而不是零风险。A=本人订单整理；B=接单池代取；C=站内点餐；D=社区求助；E=校门代取已送达物品（本次场景）。
> **口径源**：`docs/contract/V4_CONTRACT.md` §0/§1/§2/§10/§11/§13、`docs/data/V4_DATA_MODEL.md`、`docs/engineering/V4_ARCHITECTURE.md`；当前状态以根 `STATE.md` 为准。
> **取证**：微信官方文档、微信小程序备案指引、微信开放社区、中央网信办/中国政府网法规（URL 见 §10）；未拿到官方依据的均标「待核实」。平台规则会变，落地前以提交时后台要求为准。

## 0. 一页结论（给决策）

| 问题 | 结论 | 一句话依据 |
| :-- | :-- | :-- |
| 当前备案能否直接加校园墙？ | **不能** | 个人主体开放类目里没有「社交」；「社交-社区/论坛」要求非个人主体 + 非经营性 ICP 备案，首次代码审核还要过属地互联网信息内容主管部门（约 7 天） |
| 当前备案能否直接加外卖代取？ | **分形态**：E 校门代取=与快递同形态，备案不新增；B 接单池=跑腿，备案需变更 | E 没有商家/餐品/站内下单/公开抢单，本质是「已送达物品代取」；B 是平台撮合；个人微信类目都没有跑腿 |
| E 校门代取已送达外卖，会不会违反备案？ | **大概率不新增违规；备案描述要与实际一致** | E 与快递代取同属「已送达物品代取」，不是外卖平台/点餐平台；但「外卖」字样和食品属性会提高微信审核注意；建议补充备案描述，页面用「校门代取/物品代取」 |
| 只做「信息查询与整理」、不交易、不涉及款项，会不会违反备案？ | **不必然；看实际服务链** | 只记录本人已下单的外卖信息、可查/可复制/可删，属于「工具-信息查询/订单功能」；一旦有公开接单/抢单池/商家点餐/站内下单，就是跑腿或外卖平台；E（固定指派、无池、无商家）与快递同形态（见 §2.7） |
| 那做「备案变更」行不行？ | **只能解决服务内容记录，不能解决类目资格** | 备案与服务类目是两套分类；主体不变时，管局备案里能选「工具-跑腿」，但微信后台仍不会给个人主体开放「跑腿」类目；反过来，微信类目也不能替代备案 |
| 一个人 5 个上限到底卡在哪？ | **注册和绑定都卡** | 同一身份证注册个人类型小程序上限 5 个；同一身份证/手机号/微信号绑定小程序上限也都是 5 个；个体工商户注册上限 5 个、企业 50 个；备案数量个人 5、个体户 5、企业 50 |
| 新开一个小程序绕开行不行？ | **可能先撞绑定上限** | 新小程序仍要一个管理员身份去绑定；如果本人已达 5 个，需换管理员身份或先注销一个不用的；升级现有主体不新增绑定名额 |
| 推荐路线 | **A：升级现有主体；先外卖、后校园墙** | 保留 appid/用户/订单，不新增小程序名额；外卖风险中等、可先跑通；校园墙等主体/类目/备案/审核人力都到位再做 |
| 如果现有主体绝对不能动 | **B：新主体 + 新小程序（校园墙独立）** | 但会叠加 5 个绑定上限、新备案周期、UnionID/双小程序运营、两套用户心智 |
| 最不该走的路 | **C：维持个人主体，把功能包装成「信息工具」** | 运营规范 2.5.7 明确把「个人主体提供超出开放类目的服务」列为类目不符，可提醒限期整改、封禁能力直至下架；UGC 的法定义务也不会因为换个说法消失 |

**先做三件事（不写代码）**：①用户后台核对主体/类目/备案服务内容三项事实；②在「升级现有主体」与「新主体+新小程序」之间拍板；③用下面的 Q1~Q13 把产品边界（外卖是否收费、外卖做 A/B/E 哪种、校园墙是否匿名、谁来做审核）定下来。三项没定之前，任何实现都会返工。

## 1. 现状基线（只列事实）

### 1.1 备案、主体与类目

- 主体：**个人**；类目：**工具类目**（D13，2026-10-22 用户裁决）。
- 备案：**2026-11-03 用户确认完成**；仓库只记录状态与占位，真实备案号在用户后台/本地证据（`docs/delivery/review/04_类目备案与业务说明.md` §3）。
- 当前提审材料口径：**校园快递代取的信息与履约工具**；不出现「快递业务经营」「快递服务」「跑腿平台」等表述。
- **必须以用户后台为准的三项**：①主体类型是否仍为个人；②微信后台已选的类目/子类目；③小程序备案里的「服务内容」。本文结论不依赖具体子类目：**只要主体仍是个人，社交与跑腿都不在可选范围**。

### 1.2 角色与绑定模型的代码事实

- 数据层**已经支持同一 openid 同时是顾客与兼职**：`users.roles[]` 取 `CUSTOMER`/`PARTNER` 子集；`shared/role.js` 的 `pickActiveRole` 在双角色时优先兼职；`CONTRACT §1` 也写明「同一 openid 可同时是顾客与兼职，身份可切换」。
- 但入口仍是二选一：`pages/role/index.wxml` 两张卡「我是顾客 / 我是兼职」，靠 `lastRole` 给「上次使用」建议；页面文案还写着「同一个微信号可以同时是顾客和兼职，两边的数据互相隔离」。
- 绑定是 1:1：`bindings.activeKey` 保证一个顾客只有一条 ACTIVE 绑定；`order.create` 的顾客路径要求 ACTIVE 绑定；兼职只能看绑定自己的顾客与订单（`CONTRACT §1/§4.2`、`DATA_MODEL §2.4`）。
- **结论**：现在的「顾客/兼职」二元，**主要是入口、导航和绑定关系的产品选择，不是数据模型做不到多角色**。真正难的是外卖要「不绑定也能接单」、校园墙要「既不是顾客也不是兼职」——这两个会突破现有关系模型。

### 1.3 工程基线（决定改动量的分母）

- 当前页面/集合/动作/测试套件以真实取数为准（当前快照 **34 页 / 14 集合 / 89 动作 / 39 套**）：

- 单环境、零金额、无支付组件、无设备定位、无完整手机号；共享件由 `tools/sync-cloud-shared.js` 生成；云函数不得出现 `db.collection`（只经 `db/dao.js`）。
- 订单模型已经很重：7 状态、24 种事件、`parcels[]`（1~10 件）、`images[]`（0~10 张）、`delivery`（宿舍维度）、`appoint`、`transfer`、留言、清理、后台 DTO。**外卖若另起一套订单集合，会复制状态机/事件/留言/清理/通知；不建议。**更现实的是 `orders.line` + `line` 专属子块，复用状态与动作。

## 2. 平台规则与硬门槛

### 2.1 小程序数量与备案数量

| 维度 | 个人 | 个体工商户 | 企业/政府/媒体/其他组织 |
| :-- | :-- | :-- | :-- |
| 注册上限 | **5** | **5** | **50** |
| 绑定上限 | 同一身份证 5、同一手机号 5、同一微信号 5 | 同左 | 同左 |
| 备案数量上限 | **5** | **5** | **50** |

- 官方原文：同一身份证注册个人类型小程序数量上限 5；同一企业/政府/媒体/其他组织 50；同一个体工商户 5；同一身份证/手机号/微信号可绑定 5 个小程序；备案数量上限与主体类型对应（个人 5、个体工商户 5、企业等 50）。
- **对本项目的含义**：
  1. 「一个人最多 5 个」是真的，而且**注册上限与绑定上限是两道闸**；
  2. 若本人已用满 5 个，**新开小程序仍要一个管理员身份去绑定**，不是换个主体就自动多出名额；
  3. **升级现有小程序主体不新增绑定名额**，这是方案 A 相对方案 B 的结构性优势。

### 2.2 备案：新增、变更、注销与主体变更

- 审核时效（官方备案 FAQ）：平台初审 **1~2 个工作日**；各省通信管理局 **1~20 个工作日**；变更备案与新增备案时效一致；注销备案为平台即时~管局 20 个工作日。
- 变更备案**不影响小程序正常使用**（官方 FAQ §15.4）；但备案信息与小程序信息不一致时，平台可警告、封禁功能、强制注销备案（运营规范 2.5.35）。
- **主体变更（统一社会信用代码变化）不支持直接变更备案**：官方 FAQ 明确「需先注销原备案，再使用新主体重新申请备案」；微信开放社区回复「因主体变更需注销备案的，当前暂不影响小程序使用，注销后请尽快用新主体重新备案」。
- **含义**：备案可以变，但它只是「登记服务内容」；**它不能把个人主体不可选的类目变出来**。主体升级会导致备案注销+重备，需预留时间窗并准备材料。

### 2.3 类目：个人主体 vs 非个人主体（核心证据）

**个人主体开放的服务类目（官方 `material/index.md`）只有八类**：物流服务、教育服务、生活服务、餐饮服务、旅游服务、工具、商业服务、体育。**没有「社交」**。

| 能力 | 个人主体可选？ | 非个人主体对应类目 | 资质要求 | 关键限制 |
| :-- | :-- | :-- | :-- | :-- |
| 校园墙（UGC 发帖/评论/社区） | **否**（个人类目清单无社交） | **社交-社区/论坛** | 《非经营性互联网信息服务备案核准》；政府主体可用统一社会信用代码证 | 适用于 UGC 发布与交流；**首次提交代码审核需属地互联网信息内容主管部门审核确认，约 7 天**；另有内容安全、实名、举报等义务 |
| 外卖代取（代取已下单餐品） | **否**（个人「生活服务」仅丽人/家政/婚庆；「工具」无跑腿；「餐饮服务」仅餐厅排队且明确不含线上点餐/外卖） | **生活服务-跑腿** | 无 | 定义是「委托跑腿员代为购买和送达各种物品」；若做「外卖配送平台型服务」需补「餐饮服务-外卖平台」；若为多个经营者提供交易平台需补电商平台类目 |
| 现有快递代取 | **边缘**：按「工具-信息查询/信息与履约工具」申报 | 更贴合的是「生活服务-跑腿」或物流相关类目 | 视类目 | **现有产品本身已经在个人主体类目边缘**；新增外卖会把「跑腿」从隐含变成显性，审核与类目不符风险都会上升 |

同一小程序可以同时申请多个类目（数量上限以后台为准）；本案最多涉及工具、生活服务、社交三类，通常不触及上限，但每加一个类目都要过对应资质/审核。

补充证据：

- 个人主体「生活服务」清单：丽人服务（美甲/美容/美睫/美发/纹身/祛痘/纤体/舞蹈/瑜伽）、家政服务、婚庆服务；**没有跑腿、没有外送**。
- 个人主体「工具」清单：记账、日历、天气、办公、图片处理、计算器、报价/比价、信息查询、预约/报名、健康管理、备忘录；**没有跑腿**。
- 个人主体「餐饮服务」只有「餐厅排队」，且注「不包含线上点餐、外卖等服务」。
- 非个人主体「生活服务-跑腿」：资质要求 `/`，适用范围「为需求者提供委托跑腿员代为购买和送达各种物品的服务，如：食品、日用品、生活物品等」；注：涉及外卖配送平台型服务需补「餐饮服务-外卖平台」，涉及多个经营者交易平台需补「电商平台」。
- 非个人主体「社交-社区/论坛」：资质二选一（《非经营性互联网信息服务备案核准》或政府主体统一社会信用代码证）；适用范围「UGC 内容的发布与交流，如论坛、贴吧、社群」；注：首次代码审核需属地互联网主管机关审核确认，约 7 天。

### 2.4 校园墙的 UGC 合规门槛（比类目更重）

微信侧：

- **2.5.18 内容安全**：UGC 平台必须调用内容安全检测接口校验文本/图片；未设置过滤机制会被阶梯封禁分享能力、朋友圈打开能力、限制单页面处理。
- **2.10 用户产生内容规范**：服务提供者要设置过滤机制（内容安全 API、人工审核等）、建立巡查机制、对内容安全承担主要责任；被投诉要能及时回应。
- **2.5.7 类目不符**：明确把「个人主体提供超出个人主体开放类目范围的服务」列为违规；处理可从提醒限期整改到封禁能力直至下架。

法规侧：

- **《互联网跟帖评论服务管理规定》（2022-12-15 施行）**：评论/回复/留言/弹幕/点赞等都属于跟帖评论服务；要求「后台实名、前台自愿」，对注册用户做真实身份信息认证；建立审核管理、实时巡查、应急处置、举报受理制度；配备与服务规模相适应的审核编辑队伍；建立用户分级管理、黑名单、申诉制度；对新闻信息跟帖要「先审后发」。
- **《具有舆论属性或社会动员能力的互联网信息服务安全评估规定》**：开办论坛、博客、聊天室、公众账号、信息分享、**小程序**等，或附设相应功能，属于具有舆论属性/社会动员能力；上线前应自行开展安全评估，并通过全国互联网安全管理服务平台提交评估报告；功能重大变更、用户规模显著增加、发生违法有害信息传播扩散等情形也要评估。
- **实名口径提醒**：微信登录/openid 本身不等于 App 侧已完成「后台实名」认证；严格口径下需要手机号码、身份证件或校园认证等真实身份信息，具体以属地网信要求为准（见 Q4）。
- **中央网信办「清朗·2024 年暑期未成年人网络环境整治」**：明确点名「校园墙」「留言板」环节的「开盒挂人」问题；部分平台接受匿名投稿，发布攻击谩骂、曝光未成年人姓名/学校/账号等隐私；北京、河南、贵州等地解散关闭 1500 余个提供挂人服务的话题/超话/贴吧，对突出问题平台从重处罚，违法线索转公安。
- **未成年人保护**：校园墙用户可能包含未满 18 岁学生；匿名投稿、攻击谩骂、隐私曝光是高风险组合。若做，必须有未成年人保护策略（至少年龄提示、违规处置、紧急联系人/心理危机转介流程）。

工程侧（微信能力）：

- `security.msgSecCheck` v2：文本上限 2500 字，`scene` 1 资料/2 评论/3 论坛/4 社交日志，**必须带 openid**（用户近两小时访问过小程序）；返回 `suggest`=pass/review/risky；单 appId 4000 次/分钟、200 万次/天；**未上架小程序 100 次/天**。
- `security.mediaCheckAsync` v2：图片/音频异步检测，`scene` 3 论坛；**结果 30 分钟内推送到消息接收服务器**，不是同步返回；`media_url` 必须可被检测服务器下载（私有云存储要先签临时 URL）；单文件 ≤10M；单 appId 2000 次/分钟、20 万次/天。
- 含义：**图片 UGC 不是「调个接口」**，要增加消息推送接收端点、签名校验、`trace_id` 幂等、结果回写、失败重试；纯云开发栈要补 HTTP 访问服务或云托管。**MVP 建议先做纯文字墙**，图片后置。

### 2.5 外卖代取的合规边界

- **跑腿 ≠ 外卖平台**：如果小程序只让顾客录入「已经在别处下好的外卖订单」（商家、取餐号、餐品、取餐时间），由跑腿员去取并送达，属于「生活服务-跑腿」；如果小程序展示商家/菜单、让顾客在小程序内点餐下单，就变成「餐饮服务-外卖平台/点餐平台」，资质与责任完全不同。**本期设计必须明确：不做商家入驻、不做菜单、不做站内点餐。**
- **食品安全**：跑腿员只运输密封餐品，不拆封、不加工、不重新包装；平台应在页面写明「仅代取，不承担餐品制作责任」，并要求取餐时检查封签。学校对校园外卖通常有专门管理规定（校门/宿舍/配送时段/指定取餐点），**先拿校方书面要求**；《学校食品安全与营养健康管理规定》对学校集中用餐/外购食品有制度要求，校园外卖治理通常由后勤、学工、保卫处联合管理。
- **交通安全与用工**：校内电动车/自行车配送、逆行/超速/事故责任、跑腿员是否健康证（接触直接入口食品才涉及；仅运输密封餐品通常不接触，但以属地市场监管/校方要求为准）、是否给学生购买意外险——这些不是代码能解决的。
- **零金额 vs 收费**：若站内收服务费，会触发微信支付、商户号、交易类目、退款/投诉、发票/税务、资金安全等一整套；**建议 MVP 维持零金额**，跑腿员与顾客线下自行处理，平台只记录履约。若一定要站内收费，另立项目、另做主体与合规评估，不要混在本期。

### 2.6 主体变更的实际代价

- 微信小程序**主体变更**：目标主体不能是个人；个人→个体工商户/企业需要**公证书**（或符合平台要求的授权验证）；平台收取**变更审核费 300 元/次**（以后台为准）；提交后有 **7 天确认期**，逾期需重新缴费；变更成功后**原小程序数据保留**。
- 账号条件：已开通官方旗舰标、支付服务商、广告主（余额清零/解绑）等情形可能不支持或需先处理；本产品零金额、无支付，通常不触发，但仍以后台校验为准。
- 变更完成后：**备案要注销原主体备案，再用新主体重新备案**（统一社会信用代码变了）；微信类目要按新主体重新提交；社交类目还要过属地网信审核。
- **风险点**：备案注销到新备案通过之间，官方社区说法是「暂不影响使用」，但法律状态上是未备案；应把材料先备齐、注销后立即提交，尽量缩短空窗。若无法接受空窗，选方案 B（新小程序），但会叠加 5 个绑定上限与新备案周期。
- 另一个代价：主体从个人变为个体工商户/企业后，涉及工商/税务/对公账户/微信认证年审等持续义务；这不是纯技术选择。

### 2.7 「只做信息查询与整理」的备案判断（2026-11-16 补充）

判断不看口号，看**实际服务链**：谁发布、谁接单、谁取餐、谁送达、平台是否撮合。分五种形态：

| 形态 | 具体功能 | 实际服务性质 | 备案判断 | 微信类目判断 |
| :-- | :-- | :-- | :-- | :-- |
| **A 本人订单信息整理** | 顾客记录自己**已在别处下好**的外卖（商家/取餐号/时间/送达点），可查询/复制/删除；**没有他人接单、没有状态流转、没有跑腿员** | 信息记录/查询 | 属于「工具-信息查询/订单功能」，与现有「信息与履约工具」口径可以一致；**不必然违反备案**，通常无需变更 | 工具-信息查询（个人可选）；合规 |
| **B 代取撮合** | 顾客发布代取需求 → 其他用户/跑腿员**公开接单/抢单** → 取餐 → 送达 → 状态流转；不收费 | 跑腿/配送信息服务（公开撮合+履约） | 备案服务内容应包含「工具-跑腿」（个人备案可选，以管局审核为准）；若备案只写信息查询而实际上线 B，属于**备案信息与实际不一致**，存在应变更未变更的风险 | 生活服务-跑腿；**个人主体不可选** → 类目不符，不能合规上线 |
| **C 站内点餐/商家** | 展示商家/菜单，顾客在小程序内点餐下单（即使不收费） | 外卖/点餐平台 | 备案需餐饮/外卖相关服务内容；个人通常不可 | 餐饮-外卖平台，需资质；个人不可 |
| **D 社区求助** | 顾客发帖求助，他人评论/私聊表示愿意帮取 | 社交/社区或跑腿 | 备案应包含网络社交或跑腿；与信息查询不一致 | 社交-社区/论坛或跑腿；个人均不可 |
| **E 校门代取已送达物品**（本次场景） | 外卖员已把餐送到东门；顾客委托从东门取到宿舍/校内；**无商家/餐品选择、无站内下单、无公开抢单**；由绑定兼职/固定指派完成 | 已送达物品代取（信息+履约），与快递代取同形态 | **不新增服务类型**；若备案只写「快递」，建议补充/变更为「校园物品代取（快递/外卖等已送达物品）信息与履约工具」；未变更的风险低，但不是零 | 仍按工具-信息查询/订单功能口径；个人主体没有跑腿类目，「外卖」字样提高审核联想；**保持与快递完全同形态，风险≈现有快递** |

**判断规则**：

1. **零金额、不交易只排除支付/经营性风险，不改变服务分类。** A 之所以是信息查询，不是因为「不收费」，而是因为平台不撮合、不接单、不履约；B 即使全程免费，仍然是跑腿。E 不是外卖平台，但仍是「代取履约」；它的风险取决于是否与快递同形态，而不是「外卖」两个字本身。
2. **备案看「服务内容是否与实际一致」，不看功能名称。** 当前备案若只有「工具-信息查询」，而实际提供 B/C/D，应及时变更备案；E 若保持与快递同形态，通常不构成新的服务类型，但备案描述最好覆盖「物品代取（含已送达外卖）」。未及时变更，平台可按运营规范 2.5.35 警告、封禁功能、强制注销备案，管局也可能处置。
3. **备案能覆盖 ≠ 微信能上线。** 即使把备案改成「工具-跑腿」，微信个人主体仍没有「生活服务-跑腿」类目；B 仍会卡在类目不符。E 走的是与快递相同的「工具-信息查询/订单功能」口径，风险与现有快递相同，不是零。
4. **「外卖下单」这个词会被理解为 B/C。** A 的页面/文案应叫「外卖订单信息整理」「我的外卖记录」；E 应叫「校门代取」「物品代取」，不要叫「外卖下单」；但也不要用改名掩盖真实的接单/履约（运营规范 2.5.19 绕开审核）。
5. **真正的分界线是「有没有公开撮合/商家点餐」**：只记录、只查询、只整理 = A；固定指派/绑定的已送达物品代取 = E（与快递同形态）；公开抢单/平台撮合 = B；有商家/菜单/站内点餐 = C；发帖等人回应 = D。

### 2.8 为什么快递代取能通过，而外卖不能照搬这个结论

先分清两种「通过」：

| 通过类型 | 审什么 | 能证明什么 | 不能证明什么 |
| :-- | :-- | :-- | :-- |
| **备案通过** | 主体、服务内容描述、材料 | 备案手续完成 | 不能证明微信类目合规，也不能证明实际功能与描述完全一致；备案是材料审核，不逐页看代码 |
| **微信代码审核通过** | 本次提交的页面/流程/类目 | 本次审核样本被接受 | 不是法律认定；后续投诉、抽查、新功能仍可能被判类目不符（2.5.7） |

**快递代取能过，通常是因为它被呈现为「信息与履约工具」**：

- 包裹已经是顾客的，平台不做购买、商家入驻、菜单或站内点餐；
- 顾客先绑定一位兼职，1:1 封闭关系，不是公开抢单市场；
- 没有支付/收费/款项，没有公开报价/排行；
- 页面讲「取件信息整理/进度」，不是「跑腿平台」。

这使审核更可能把它归到「工具-信息查询/订单功能」，而不是「生活服务-跑腿」。**但这是审核判断，不是永久合规认定**：备案是材料审核，描述与实际的偏差仍可能被要求变更；微信审核是抽样，后续投诉/抽查/新功能仍可能触发类目不符处置；现有快递代取本身就在个人主体类目边缘，新增外卖会放大这个边缘。

**B/C/D 不能照搬这个结论；E（校门代取已送达物品）可以参照快递**：

- E 没有商家、没有餐品选择、没有站内下单、没有公开抢单，和快递一样是「已送达物品代取」，不是外卖平台；
- 但「外卖」两个字和食品属性会提高审核注意：页面应叫「校门代取」「物品代取」，不要叫「外卖下单」；描述里可写「含已送达校门的外卖等物品」；
- E 必须与快递保持同一形态：绑定兼职/固定指派、不公开抢单、不做商家/菜单、不站内点餐、不涉及支付/收费；
- 备案描述若只写「快递」，建议补充/变更为「校园物品代取（快递/外卖等已送达物品）信息与履约工具」；微信类目风险与现有快递相同，不是零；
- 一旦加入公开抢单、商家、餐品选择、站内下单，就升级为 B/C，不再是 E，前面的结论不再适用。

> 仓库记录只显示**备案已完成**；微信代码审核是否已通过、以你后台为准。如果目前只是备案通过，那它本来就不能证明微信类目合规；快递审核通过可以作为 E 的参照，但不能作为 B 的先例。

## 3. 两项能力的可行性

### 3.1 校园墙：不是「加一个页面」，是「加一个受监管的 UGC 业务」

**可行形态（如果要做）**：

| 维度 | 建议 MVP | 明确不做 |
| :-- | :-- | :-- |
| 身份 | 微信登录 + 校园身份门槛（复用已完善的宿舍资料 + 校园邀请码/人工审核，二选一）；后台实名、前台匿名别名 | 不采集身份证/学生证照片（除非 Q4 决定要做强认证）；不展示真实姓名/宿舍/手机号 |
| 内容 | 纯文字 + 板块（失物招领/求助/活动/校园信息）；标题 + 正文 ≤ 规定字数；敏感词 + `msgSecCheck` | 不做图片（首期）、不做私信、不做陌生人交友、不做二手交易、不做打赏/收费、不做定位 |
| 互动 | 先审后发；首期可只做「点赞 + 举报」，评论后置或同样先审后发 | 不做匿名私信、不做「表白匹配」、不做排行榜/热榜（避免算法推荐备案与网暴放大） |
| 审核 | 管理员审核队列（通过/驳回/隐藏/删除/封禁）；举报入口；申诉入口；违规记录 | 不做「先发后审」的匿名墙；不做无人值守 |
| 运营 | 至少 1~2 名审核员 + 一份审核 SOP + 紧急处置联系人；日志留存不少于 6 个月（《网络安全法》第二十一条）；安全评估报告 | 不在没有审核人力的情况下上线 |

**为什么说「个人主体不能直接加」**：不是技术问题，是主体类目问题。个人主体连「社交」大类都没有；即使把功能写成「信息展示」，只要用户能发帖、别人能看、能评论，就是 UGC 社区，审核会按社交类目看。运营规范 2.5.7 对「个人主体超出开放类目」有明确处置口径。**用「工具-信息查询」包装匿名墙，是把审核当运气，不是合规路径。**

**运营成本**：校园墙的真实成本在审核与处置，不在代码。匿名投稿 + 攻击谩骂 + 隐私曝光是已经被网信办点名的组合；一旦出现「开盒」或未成年人事件，主体（个体工商户/企业）要承担平台责任。**如果没有人能每天看队列、处理举报、写处置记录，建议不要做匿名墙。**

### 3.2 外卖代取：技术可复用，但类目与运营要单独过关

**可行形态（如果要做）**：

1. 顾客在别处下好外卖，进入小程序选择「外卖代取」；
2. 录入/截图识别：商家名、取餐号（或订单尾号）、餐品简述、取餐时间窗、送达地点（宿舍/教学楼/校门/指定取餐点）、备注；
3. 进入**接单池**：符合「已开通外卖线 + 在服务范围 + 当前可接单」的跑腿员看到有限信息（商家、取餐时间、送达楼栋、备注），**看不到顾客姓名/头像/昵称/完整房间号**；
4. 跑腿员接单（原子抢单）→ 到店取餐（核对取餐号/封签）→ 送达 → 标记送达 → 顾客确认/超时自动完成；
5. 异常：商家出餐慢/缺货、餐品洒漏、错拿、超时、联系不上；平台只记录与协调，不涉及退款（零金额）。

> **如果只做 A（本人订单信息整理），不要接单池、不要状态流转、不要跑腿员入口**；A 属于「工具-信息查询」，不是本节的代取。**E（校门代取已送达物品）也不走接单池**：复用快递的绑定/固定指派，只是取件点变成东门、物品可能是外卖；它和快递同形态，备案不新增，微信风险同现有快递。本节描述的是 B（公开接单池/平台撮合），备案与微信类目的门槛按 §2.7 判断。

**与现有快递代取的关键差异**：

| 维度 | 快递代取（现状） | 外卖代取（新增） |
| :-- | :-- | :-- |
| 关系 | 顾客先绑定一位兼职，1:1 | **不绑定**，接单池抢单；否则高峰无人接单 |
| 时效 | 可预约到最晚时间，日结完成 | **强时效**（30~60 分钟），超时即异常；自动完成窗口要短 |
| 地址 | 宿舍（苑/栋/宿舍号） | 宿舍 + 教学楼/图书馆/校门/取餐点；要扩展地址模型 |
| 身份可见 | 绑定双方可见头像/昵称 | **接单前不可见顾客身份；接单后也只给履约必需信息**（楼栋/房间/备注），不给头像/昵称 |
| 取件凭证 | 取件码/柜号/运单尾号 | 取餐号/订单尾号/商家名；不存完整手机号 |
| 餐品安全 | 包裹封口 | 封签/洒漏/错拿；需要取餐检查项与异常码 |
| roomTag | 有（同兼职同宿舍区分） | **不需要**；外卖不建立长期关系 |
| 收费 | 零金额，线下 | 建议同样零金额；若站内收费则另立项目 |

**技术要点**：

- 订单加 `line='TAKEOUT'` 与 `takeout{merchantName,pickupNo,mealText,pickupWindow,sealed}` 子块；`delivery` 扩展 `kind=DORM|TEACHING|GATE|OTHER`；旧单默认 `EXPRESS`，零迁移。
- 新增 `order.listPool` 与 `order.claim`（或 `acceptPool`）：按 `line/status/区域/时间` 查池；抢单用事务 + 版本 CAS，防双接；池内订单超时未接自动取消/退回。
- 新索引：`(line,status,zone,createdAt)`、`(line,status,pickupWindow)`；具体以 DATA_MODEL 索引表为准。
- 复用 7 状态：`SUBMITTED→ACCEPTED→PICKED→DELIVERED→COMPLETED`，异常/取消分支不变；事件可复用 `ORDER_CREATED/ACCEPTED/PICKED/DELIVERED/COMPLETED`，如需要再补 `TAKEOUT_*` 语义事件（能不加就不加）。
- DTO 分支：池列表不返回顾客身份；接单后返回楼栋/房间/备注；顾客侧只看到 `partnerNo`，不返回跑腿员头像/昵称（与 D58 转派口径一致）。
- 通知：送达提醒可复用 D73 的订阅模板；池新单提醒可先用工作台红点/轮询，不急着加模板。

**风险**：校方是否允许外卖进校/进宿舍；餐品丢失/洒漏的责任；跑腿员交通安全；高峰无人接单；恶意刷单/放鸽子；食品封签争议。**这些要靠运营规则与校方沟通，不靠代码。**

### 3.3 三条服务线组合

| 服务线 | 关系模型 | 主要数据 | 主要风险 |
| :-- | :-- | :-- | :-- |
| 快递代取 `EXPRESS` | 1:1 绑定 + roomTag | 现有 `orders`/`bindings` | 现有类目边缘风险；继续保持现状 |
| 外卖代取 `TAKEOUT` | 接单池，不绑定 | `orders.line='TAKEOUT'` + `takeout` 子块 | 类目、校方、食品安全、时效 |
| 校园墙 `WALL` | 无关系，公开内容 | 新集合 `wall_*` | 类目、UGC 审核、未成年人、网暴/开盒、安全评估 |

## 4. 角色模型优化（本次最该先想清楚的部分）

### 4.1 问题不是「顾客/兼职二选一」，而是「把关系当成了人的类型」

- 现状把「顾客」「兼职」当成两种人；但同一个人可以今天下单、明天跑腿；校园墙用户既不下单也不跑腿。
- 外卖又要求「不绑定也能接单」，说明「兼职」不等于「被某顾客绑定的人」；绑定只是快递线的一种关系。
- 所以目标模型应该是：**账号（Account）—能力（Capability）—服务线（Service Line）—关系（Relationship）**，而不是「一个账号一个角色」。

### 4.2 目标模型

| 层 | 对象 | 说明 |
| :-- | :-- | :-- |
| 账号 | `users`（openid） | 一个微信身份；`users.roles[]` 保留兼容；新增能力判断不靠角色字面量 |
| 能力 | `ORDER` / `RUN` / `POST` / `MODERATE` | 下单、接单履约、发帖互动、审核管理；同一账号可同时具备多个 |
| 服务线 | `EXPRESS` / `TAKEOUT` / `WALL` | 快递代取、外卖代取、校园墙；页面/配置/统计按线区分 |
| 关系 | `BINDING` / `POOL` / `NONE` | 快递=1:1 绑定；外卖=接单池；校园墙=无关系 |
| 业务对象 | `orders.line` / `wall_posts` | 订单加线字段；墙内容独立集合 |

**一句话**：`PARTNER` 不再是「一种人」，而是「已开通接单能力」；`CUSTOMER` 不再是「一种人」，而是「下过单/有下单能力」；校园墙用户不需要先成为顾客或兼职。

### 4.3 三条线的差异（产品与权限）

| 维度 | 快递 `EXPRESS` | 外卖 `TAKEOUT` | 校园墙 `WALL` |
| :-- | :-- | :-- | :-- |
| 准入 | 顾客默认；兼职邀请码 | 顾客默认；跑腿员需开通外卖线 | 微信登录 + 校园门槛；发帖需通过内容规则 |
| 关系 | 顾客绑定一位兼职 | 不绑定；池内抢单 | 无 |
| 顾客可见 | 绑定兼职头像/昵称（D19/D42） | 仅 `partnerNo`；无头像/昵称 | 他人只见匿名别名 |
| 跑腿员可见 | 绑定顾客资料（头像/昵称/宿舍/尾号） | 接单前仅商家/时间/楼栋；接单后房间/备注；无头像/昵称 | 不适用 |
| 订单/内容 | 现有 7 状态 | 复用 7 状态 + 强时效 | 内容状态：待审/通过/驳回/隐藏/删除 |
| 计费 | 零金额 | 零金额（建议） | 不涉及 |
| 审核 | 现有异常/客服 | 异常码 + 线下协调 | 先审后发 + 举报 + 申诉 + 封禁 |

### 4.4 导航与入口（低风险迁移）

**M1（先做，改动小）**：

- `pages/role` 不再是「二选一」，改为「继续使用」+ 三张服务卡（快递代取/外卖代取/校园墙）；有 `lastRole` 时直接给出「继续上次」；没有则默认顾客首页。
- 「我的」增加「切换工作台」：顾客首页 ↔ 接单工作台（仅已开通接单时显示）；不再要求重新选身份。
- 顾客首页增加服务卡；接单工作台增加「外卖池」入口（若已开通）；校园墙入口按能力显示。
- 服务端鉴权从「角色是否等于」改为「能力是否具备 + 资源是否归属」；`users.roles` 保留，避免数据迁移。

**M2（外卖上线时）**：订单列表加服务线筛选；外卖下单/详情/池页面；跑腿员服务配置加「外卖线」开关与范围。

**M3（校园墙上线时）**：墙首页/详情/发布/我的发布；管理员审核台；如流量大再考虑统一 4 tab 壳（首页/订单/消息/我的）替代按角色切 tab。

**不建议一上来做「统一大首页 + 全部重写」**：现有 34 页、7 状态、24 事件、89 动作的回归面太大；M1 先拆掉「强制二选一」，M2/M3 再按线加页面，风险可控。

### 4.5 需要修订的现有口径（不是本文能定的）

| 现有口径 | 需要怎么改 | 影响 |
| :-- | :-- | :-- |
| D4/D20：顾客只能绑一个兼职；兼职不能绑顾客 | 明确**只适用于快递线**；外卖线是池，不建立绑定 | `bindings` 语义、`order.create` 守卫、权限矩阵、后台绑定视图 |
| D13：个人主体+工具类目 | 改为非个人主体+对应类目，或明确「不新增」 | 备案/类目/提审材料/隐私文本 |
| D19/D42：头像昵称仅绑定对方可见 | 外卖池不返回顾客头像/昵称；墙不展示头像/昵称；需补披露 | DTO、隐私文本、QA |
| D5/D6/D30：零金额 | 外卖线继续零金额；若站内收费则另立项目并改口径 | 支付/交易/退款/发票/税务 |
| D73：订阅消息 | 外卖送达可复用；墙回复/点赞不建议首期加 | 模板、授权、额度 |
| §11 隐私 | 新增墙的公开内容、匿名、举报、审核、留存、注销；外卖地址扩展 | 隐私文本版本、同意、后台声明 |

## 5. 方案对比与推荐

### 5.1 方案 A：升级现有小程序主体（推荐）

**路径**：

1. 注册个体工商户/企业（经营范围建议含「外卖递送服务/居民日常生活服务/互联网信息服务」等，以当地市场监管为准）；
2. 微信认证（如目标主体未认证）；
3. 现有小程序「主体变更」：个人→非个人，需公证/授权验证，300 元/次，7 天确认期；变更后 appid、用户、订单数据保留；
4. 注销原主体的小程序备案 → 用新主体重新备案（服务内容先加「工具-跑腿」，后续再加「网络社交」）；
5. 微信后台加类目：先「生活服务-跑腿」，外卖跑通后再评估「社交-社区/论坛」；
6. 提审：外卖线与角色 M1 一起上；校园墙另批。

**优点**：不新增小程序名额；保留 appid/用户/订单；一个审核面；可以先外卖后墙；后台/客服/数据只有一套。

**代价与风险**：公证/300 元/7 天/备案注销重备空窗；主体变个体户/企业后的工商税务义务；社交类目属地网信审核；UGC 审核人力；现有快递线在主体变更期间不能出问题。

### 5.2 方案 B：新主体 + 新小程序（校园墙独立）

**路径**：新注册个体工商户/企业 → 新小程序 → 备案 → 类目 → 校园墙；现有个人小程序继续做快递/外卖（但外卖仍卡个人类目，所以外卖也得进新小程序或另升级）。

**优点**：校园墙风险隔离；即使墙被下架，不影响快递/外卖；新主体有 5 个注册名额（但绑定仍受同一身份证 5 个限制）。

**代价与风险**：**5 个绑定上限**可能直接卡住；新备案 1~20 个工作日；两个小程序、两套用户/订单/客服；跨小程序账号要用微信开放平台 UnionID（同主体/关联主体绑定；同主体最多 50 个、异主体最多 5 个；一个小程序只能绑一个开放平台账号）；校园墙冷启动没有现有用户；双份运营成本。

### 5.3 方案 C：维持个人主体，把功能包装成「信息工具」（不推荐）

- 运营规范 2.5.7 明确把「个人主体提供超出开放类目的服务」列为违规；处理可从提醒限期整改到封禁能力直至下架。
- UGC 的法定义务（实名、审核、举报、安全评估、未成年人保护）不会因为叫「信息展示」而消失；匿名墙尤其明显。
- 这不是「省备案」的捷径，是「把下架风险留给未来」；一旦在校园内传播开，处置成本更高。
- **替代形态（不是规避）**：如果只是需要「墙」的传播效果，可以用公众号/视频号/校内社群发布内容，小程序只做展示或入口；但公众号/社群同样受内容监管，且不是小程序内 UGC，不能用来绕开类目与审核。

### 5.4 方案 D：只做一条线

- **D1 只做外卖**：主体升级 + 跑腿类目 + 外卖线；不做墙。风险中等、范围可控，能先验证「多服务线 + 池」。
- **D2 只做校园墙**：主体升级 + 社交类目 + 审核人力；风险高，且没有外卖的现金流/频次支撑（如果业务上需要）。
- **推荐 D1 作为第一阶段**；墙作为第二阶段 gate。

### 5.5 对比表

| 维度 | A 升级现有主体 | B 新主体+新小程序 | C 维持个人包装 | D1 只做外卖 |
| :-- | :-- | :-- | :-- | :-- |
| 合规性 | 可做到合规（类目/备案/审核） | 可做到合规 | **不合规**（类目不符） | 可做到合规 |
| 5 个上限 | 不新增名额 | 可能撞绑定上限 | 不涉及 | 不新增名额 |
| 账号/数据 | 保留 | 分裂/需 UnionID | 保留 | 保留 |
| 备案 | 注销重备（有窗口） | 新备案（慢） | 不变 | 注销重备 |
| 校园墙 | 可做（需审核人力） | 可做（隔离） | 高风险 | 不做 |
| 外卖 | 可做 | 可做（但新 app 无存量用户） | 高风险 | 可做 |
| 时间 | 主体/备案 2~6 周 + 工程 | 新备案 + 双 app 工程 | 快但不可持续 | 主体/备案 + 工程 |
| 主要风险 | 备案空窗、UGC 运营 | 绑定上限、双运营、UnionID | 下架/封禁 | 校方/食品安全 |

### 5.6 推荐结论

**推荐 A + D1 先行**：

1. 先升级主体、加「生活服务-跑腿」、变更备案；
2. 先做外卖线 + 角色 M1（去掉强制二选一）；
3. 外卖稳定运行、审核/异常/校方流程跑通后，再评估加「社交-社区/论坛」与校园墙；
4. 校园墙的 go/no-go 不取决于代码，取决于：**审核人力是否到位、安全评估是否完成、校方/属地网信沟通是否完成、主体是否能承担 UGC 责任**。四项缺一，就不做。

如果用户明确「现有个人小程序绝对不能动」：选 B，但先查本人身份证/手机号/微信号的 5 个绑定名额是否已满；满了就先注销一个不用的或换管理员身份，否则新小程序连绑定都过不去。

### Phase 0：裁决与外部准备（用户，0 代码）

- 外部准备：个体工商户/企业经营范围、微信认证、公证、校方沟通、属地管局/网信咨询；

### Phase 1：主体/类目/备案 + 外卖线 + 角色 M1

- 主体变更、备案注销/重备、加「生活服务-跑腿」类目；

- **Gate G1**：类目/备案通过；外卖真机全流程通过；无 P0；`check.ps1` 0；用户点检签字。

### Phase 2：校园墙 MVP

- 加「社交-社区/论坛」类目；备案服务内容加「网络社交」；安全评估报告；
- `wall_posts/wall_comments/wall_reports/wall_likes`；先审后发；举报/申诉/封禁；管理员审核台；
- 纯文字 + 板块；校园身份门槛；匿名别名；无图片/无私信/无交易；
- 审核 SOP、值班表、紧急处置联系人、日志留存、未成年人保护说明；
- **Gate G2**：属地网信审核通过；安全评估提交；审核人力到位；校方无异议；否则不做墙。

### Phase 3：增强

- 图片（`mediaCheckAsync` + 消息推送端点）、评论、回复通知、热榜/算法推荐（如做，需评估算法备案）、数据看板；
- 每项单独评估合规与审核成本，不默认全做。

**时间/成本粗估（假设 1~2 名开发，不含外部审批等待）**：

| 阶段 | 工程 | 外部 | 说明 |
| :-- | :-- | :-- | :-- |

| Phase 1 | 4~8 周 | 备案 1~20 个工作日 + 主体变更审核 | 外卖 + 角色 M1 + 测试/真机 |
| Phase 2 | 6~10 周 | 社交类目属地审核约 7 天 + 安全评估 | 墙 + 审核台 + SOP |
| Phase 3 | 按项评估 | 按项 | 图片/评论/推荐 |

> 以上是排期估算，不是承诺；外部审批、校方政策、审核人力是主要不确定项。
