## 0. 一页速览（审核可直接读这三句）

1. **本小程序是什么**：面向在校学生的校园快递代取**信息与履约工具**——顾客提交取件信息、兼职按信息取件并送达、双方在同一订单里同步进度；不经营快递业务、不承揽运输合同。
2. **主体与类目**：个人主体；按 **D13 已裁决口径**申报**工具类目**（子类目以后台实际可选为准，按 §2.2 顺序调整，**不得以不实类目提审**）。
3. **与交易无关**：全链路零金额——没有支付组件、没有账目字段、没有账目状态；订单状态只表达履约进度；统计只有单量（自证命令见 §5.3）。

## 1. 产品定位与服务范围

### 1.1 一句话定位

校园快递代取（v4）是**信息与履约工具**：顾客把取件信息（站点、取件码、柜号、宿舍）整理成订单，兼职按订单去驿站取件并送达，双方在同一订单里看进度、留言与处理异常。

### 1.2 服务范围（做）

| 角色 | 能做什么 | 不能做什么 |
| :-- | :-- | :-- |
| 顾客 | 完善资料（昵称/头像/宿舍/尾号可选）、凭完整兼职编号**自己发起绑定**、上传截图或手填取件信息下单、查看进度/留言/取消/确认送达、在「我的」管理资料与注销、在「取件清单」用本机「我的取件码」自查（D57） | 不能查看他人订单；不能绑定多个兼职；绑定只能由顾客发起（D20） |
| 兼职 | 凭邀请码激活（D13 之外由运营者发放）、配置服务类型与苑范围、接单/取件/送达/异常上报、代客下单（为没有使用本程序的顾客录入，不产生绑定）、客户档案与单量统计 | 没有添加/绑定顾客的入口（D20）；不能操作真实用户账号 |
| 开发者（白名单） | 后台治理：订单/顾客/兼职/邀请码/配置/审计、识别失败复核、**账号切换**（真实账号只读、测试账号可写） | 不能切换微信登录账号（平台不支持）；不能替真实用户操作（D14/D18） |

### 1.3 零金额业务模型（D13 / D6 / D30）

- 本程序只做「信息整理 + 履约进度」，**不涉及任何金钱交易**；不设任何价目、不提供付款入口、不生成账目、不做对账。
- **服务类型只表达「做什么」**（D41 两档）：标准代取＝送到寝室门口（上楼）；送至楼下＝送到宿舍楼下或约定地点（不上楼）。历史「送寝上门」停用仅历史订单展示。
- 交易不在小程序内发生（D30 边界）：本程序不参与交易、不处理任何资金；线下事项与本程序无关，页面与接口中也无相关字段。
- 自证：源码/页面文案/文档三个范围的零金额扫描为 0 命中（§5.3）。

## 2. 类目选择与备选顺序（D13）

### 2.1 已裁决口径

- 主体：**个人**；类目：**工具类目**（用户 2026-10-22 确认，D13 留痕；见 `docs/contract/V4_DECISIONS.md` §D13）。
- 提审材料统一按「**校园快递代取的信息与履约工具**」表述；**不出现**「快递业务经营」「快递服务」「跑腿平台」等可能被理解为经营资质的表述。
- 类目、产品描述、截图、审核说明四者必须一致，且都能在真实功能中对得上。

### 2.2 子类目选择原则

- 以后台「类目」页**实际可选项**为准；本文件不预设后台不存在的子类目名。
- 优先在**工具**大类下，选与「信息记录/效率辅助/校园生活工具」最接近、且**不要求企业主体或行业资质**的子类目。
- **不得**选择需要前置审批或资质的类目来「提高通过率」；也不得为了匹配类目而改写功能描述。

### 2.3 备选顺序（D13 留痕，逐级降级；不得跳级也不得反向）

1. **换更贴近的子类目**：同样属于工具大类、描述更匹配信息与履约工具的子类目。
2. **调整产品描述/截图**：仍以真实功能为准，只调整表述与展示重点（不新增功能、不虚构场景）。
3. **企业主体**：注册/认证企业主体后选择更贴合的类目（需要资质时按平台要求提供）。
4. **仅体验版内部使用**：不公开发布，只做体验版验证（用户与体验成员）。

> 每一级动作与结果都要留证（类目页截图 + 描述文本 + 平台反馈/驳回记录），按 §2.5 归档。

### 2.4 不得以不实类目提审（硬约束）

- 不得选择与实际功能不符的类目（例如把代取信息工具申报为电商/交易类目）。
- 不得为通过审核而虚构功能、虚构使用场景或隐藏真实功能（隐私与类目描述都会与实际行为交叉核对）。
- 不得把需要资质的经营活动包装成工具类目来规避资质要求；本产品的边界是「不经营快递业务、不参与交易」（§1.2/§1.3），类目表述必须落在该边界内。
- 类目/描述一旦调整，须同步更新提审材料与本文，并在 §2.5 留证。

### 2.5 驳回应对与证据留存

| 驳回表述（可能） | 处理动作 | 证据 |
| :-- | :-- | :-- |
| 类目与主体资质不符 | 按 §2.3 顺序逐级处理；先确认后台该子类目对个人主体是否可选 | 类目页截图 + 平台反馈原文 |
| 类目与功能不匹配 | 调整描述与截图（真实功能），必要时换成更贴近子类目 | 描述文本 + 截图 |

## 3. 小程序备案要点（个人主体）

### 3.1 为什么必须做

未完成备案的小程序**不得上架/发布**（平台硬要求，2023 年起新注册小程序须先备案；存量小程序也须在平台要求的期限内完成）。备案是**平台+通信管理局**流程，不是代码能力，只能由主体本人办理。

### 3.2 后台位置与步骤（以后台实际页面为准）

- 位置：微信公众平台 → **设置 → 基本设置 → 小程序备案**（入口名称与字段以后台实际页面为准）。
- 典型步骤：①填写**主体信息**（个人身份证实名信息）；②填写**负责人信息**（个人主体通常为本人）；③填写**小程序信息**（名称、服务内容类型、功能简介）；④上传证件、完成人脸核验与短信核验；⑤平台初审 → 通信管理局审核；⑥获得备案号并在后台显示备案状态。
- 时间与材料以平台提示、通信管理局要求为准，本文件不预设时长。

### 3.3 个人主体要点

- 主体 = 个人身份证实名；负责人 = 主体本人；联系方式真实可接通（审核可能回拨）。
- 服务内容类型与类目/产品描述一致（按 §1.1 的「信息与履约工具」口径填写）。
- 不得涉及需要前置审批的内容（新闻、出版、教育、医疗、金融等）；本产品均不涉及。
- 名称、简介、功能必须与小程序实际一致；后续变更（名称/主体/类目/服务内容）须做**备案变更**。

### 3.4 本产品备案口径（可直接粘贴）

`本小程序为校园快递代取的信息与履约工具：顾客提交取件信息，兼职按信息取件并送达，双方在同一订单中同步进度。不经营快递业务，不涉及任何金钱交易，不提供付款或账目功能，不采集设备定位，不采集完整手机号。`

### 3.5 顺序与证据

- 顺序：**先备案 → 再提审 → 再发布**（未备案不得上架；与 D13 类目确认同为提审前置）。
- 证据：备案状态截图；备案号 `{{备案号}}`；变更记录（如发生）。归档到 `docs/delivery/V4_REVIEW_MATERIALS.md` §5 证据表。

## 5. 不涉及交易/支付/账目的论证段（审核可直接引用）

### 5.1 论证要点

1. **无支付组件**：全仓没有支付相关接口与组件、没有支付回调，也没有任何外部支付跳转。
2. **无账目字段**：订单、顾客、兼职、配置的数据结构中没有账目类字段，也没有任何与钱款相关的数值字段；接口返回体与后台列表同样没有。
3. **状态机只表达履约**：订单状态只有「待接单 → 已接单 → 已取件·配送中 → 已送达·待确认 → 已完成」，另加「异常·待处理」「已取消」分支（`shared/enums.js`）；没有任何账目状态。
4. **统计只有单量**：兼职统计页与总览只给单量、完成量、状态分布、异常数，没有收入/账期/报表指标。
5. **页面无相关区域**：顾客与兼职所有页面都没有价目表、订单账目区或类似入口；截图可逐页核对。
6. **文案口径一致**：隐私指引、用户协议、类目说明、审核材料使用同一零金额口径（端内帮助页也有固定说明）。

### 5.2 可直接粘贴的审核说明段

`本小程序为校园快递代取的信息与履约工具，不涉及任何金钱交易：没有支付组件、没有账目字段、没有账目状态；订单状态只表达履约进度（待接单、已接单、已取件、已送达、已完成，另有异常与取消分支）；统计只提供单量与状态分布。服务类型只描述做什么（送到寝室门口或送到宿舍楼下），不承载任何数量或费用信息。因此演示不会出现任何交易或账目环节。`

## 7. 账号切换与测试账号治理说明（审核可能追问）

### 7.1 平台事实（先说清楚，避免误解）

- 小程序平台**不能切换登录的微信账号**；所谓的「切换账号」不是换微信登录，而是开发者以某个账号身份进入页面查看/验收。
- 登录本身仍由微信完成；开发者也是普通微信账号，只是其微信号在云函数环境变量 `ADMIN_OPENIDS` 白名单内（白名单是唯一门槛，前端隐藏不作为安全边界）。

### 7.2 真实账号：只读

- 开发者选择真实顾客/兼职后进入会话默认 **READONLY**：顶部黄条常驻；**写操作前端置灰 + 服务端拒写**（双保险，返回 `FORBIDDEN`）。
- 会话票据：`admin.viewAsStart` 签发 32 位随机票据、服务端存储、客户端只放内存（**不写入本地存储**）、默认 30 分钟（`config.viewTicketTtlMinutes`，5~60 可配）、同一开发者同时只有一个会话。
- 审计：`ACCOUNT_SWITCH_START/END/EXPIRED` 落审计（`shared/audit-actions.js`）；退出/过期/目标注销即失效。

### 7.3 测试账号：后台合成、可写、隔离

- 后台「切换账号 → 测试账号」创建：合成标识（无真实微信账号）、昵称由开发者填写、默认头像；仅用于一个微信号单机验收两端。
- 测试会话为 **TEST_WRITE**：蓝条 + 每页 `TEST` 角标；只能写测试数据（`orders.isTest=true`、事件记 `impersonatedBy`）。
- 隔离：测试与真实账号**不能互相绑定、互相下单**（`FORBIDDEN`）；测试数据不计入统计、不进真实用户列表；按 `config.testDataRetentionDays`（默认 30 天，7~90 可配）清理；删除测试账号级联删数据（先 dry-run、再确认、写审计 `TEST_ACCOUNT_DELETE`）。
- 管理动作：`admin.createTestAccount/listTestAccounts/deleteTestAccount/purgeTestData`；前端 `pkg-admin/pages/account-switch/index`。

### 7.4 审核材料里的写法（可直接粘贴）

`开发者后台仅对云函数环境变量白名单内的运营者微信号开放，无自助注册、无口令/二维码入口；普通用户与审核员账号均无入口，因此后台体验以随附录屏 + 分步截图提交。后台中「切换账号」不是切换微信登录账号：真实账号只读（黄条 + 服务端拒写 + 全程审计），测试账号是运营者在后台创建的合成账号（蓝条 + TEST 角标，只写测试数据、不计统计、按期清理，与真实账号严格隔离）。`

### 7.5 代码落点

`cloudfunctions/api/handlers/admin/viewAsStart.js`/`viewAsEnd.js`、`cloudfunctions/api/middleware/switch-session.js`（READONLY 读白名单/写拒绝）、`admin_view_sessions` 集合、`cloudfunctions/api/handlers/admin/testAccounts.js` 与 `_test-account-ops.js`；门店隔离与清理的断言取数 `node tools/selftest.js`（真实输出为准）。

## 8. 审核可能追问的 10 个问题与标准答复（可直接粘贴）

**Q1 为什么审核员进不去开发者后台？**
`开发者后台只对云函数环境变量白名单内的运营者微信号开放，没有自助注册、没有口令或二维码入口——这是防止越权访问用户数据的安全设计，普通用户与审核员账号都无入口。因此后台演示以随附的录屏 + 分步截图提交；如需实机体验，可由运营者另行安排（无法预知审核员账号，不能临时加白名单）。`

**Q2 只有一个微信号（或有两个微信号）怎么办？**
`不需要额外账号：顾客与兼职可用同一个微信号在同一台手机上切换身份；兼职端用本条说明随附的一次性审核邀请码激活；完整履约可用兼职端「代客下单」单机走通（新顾客路径，不需要绑定、不需要第二个账号）。绑定后的双端流程以随附录屏提供。小程序平台本身不支持切换登录的微信账号，因此本产品也不要求、不提供额外微信账号的验收方式。`

**Q3 截图识别是否上传第三方？**
`仅在本地识别站点或取件码失败、且运营者开启兜底开关时，由云函数把去敏后的截图文字发给第三方大模型服务（DeepSeek）做结构化识别辅助；不发送原图、不发送微信账号标识/联系方式/头像/昵称，不用于训练。原图不出本程序云存储；识别失败原图仅白名单开发者在复核页临时查看（短时临时链接 + 每次审计 + 默认 30 天删除）。客户端不直连第三方，Key 只存云函数环境变量；开关关闭或服务不可用时自动降级为手动填写，不阻断下单。`

**Q4 隐私弹窗与拒绝路径是什么？**
`启动页先展示隐私提示、用户阅读后同意；未同意时不调用相册、摄像头、头像选择、剪切板等隐私接口，也不继续写操作。用户点「暂不同意」会停留在启动页，可再次查看/同意，不反复纠缠。非必要信息均可拒绝：头像可拒绝（用默认头像）、手机尾号可留空、取件码截图可不上传而直接手填、本单配送地址可不填（默认送到本人宿舍）。`

**Q5 为什么选工具类目？是否属于快递业务经营？**
`本小程序不经营快递业务：不承揽快递运输合同、不揽收/转运/派送经营快递，只做「顾客提交取件信息 → 兼职按信息取件并送达」的信息与履约工具；因此按个人主体 + 工具类目申报（已裁决口径）。若后台有更贴近的子类目，会按「换子类目 → 调整描述 → 企业主体 → 仅体验版」的顺序逐级处理，不以不实类目提审。`

**Q6 有没有支付或交易功能？**
`没有。不涉及任何金钱交易：没有支付组件、没有账目字段、没有账目状态；订单状态只表达履约进度；统计只有单量与状态分布；服务类型只描述送到哪里（寝室门口/宿舍楼下），不承载任何费用信息。演示中不会出现任何交易或账目环节。`

**Q7 测试账号和演示数据是真的吗？**
`测试账号是运营者在后台创建的合成账号：没有真实微信账号、昵称由开发者填写、默认头像，仅用于一个微信号单机验收两端。测试数据带测试标记，与真实账号严格隔离（不能互相绑定/下单）、不计入统计、不进真实用户列表，并按配置定期清理；删除测试账号会级联删除其数据并记审计。演示中如需展示真实流程，使用随附录屏。`

**Q8 头像和昵称怎么采集、谁能看到？**
`昵称用微信昵称输入组件采集（必填、可改、可手填，最多 20 字，保存前经内容安全检查）；头像用微信头像选择组件采集（自愿，可拒绝→默认头像，不超过 200KB）。二者只向与你存在当前有效绑定关系的对方展示：绑定前不展示头像，绑定成功后才可见；解绑、兼职停用或顾客注销后立即停止展示。后台列表不展示头像、昵称脱敏；分享卡片、通知、日志都不含头像与昵称。`

**Q9 用户数据怎么删除和注销？**
`注销入口在「我的 → 账号 → 注销账号」：有进行中订单会先拦截并提示处理；注销后唯一编号作废、资料匿名化、头像与截图文件删除，并在 30 天内物理删除（法律要求保留的除外）。已完成订单可「删除记录」（7 天后物理删除）；截图按 7 天、识别失败记录按 30 天自动删除；本机「我的取件码」清单可随时删除单条或一键清空，清空不可恢复。`

**Q10 取件清单里的取件码存在哪里？兼职和后台能看到吗？**
`取件清单页的「我的取件码」只存在顾客本人这台手机上：不上传、不进服务端、不生成订单、不强制绑定；兼职端与开发者后台（含只读视角）都看不到，也不进入日志、通知、分享卡片；可随时删除单条或一键清空，换手机或清缓存即丢失。截图识别在设备本地完成，不上传截图、不外呼第三方（已按 D57 在隐私指引中披露）。`
