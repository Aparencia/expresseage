## 1. 结论先行

**一句话**：用户要的"配送中看兼职在哪一栋"**可行**，但可行路径不是 GPS，而是「**状态驱动 + 兼职关键节点自报楼栋**」——零定位权限、零坐标、不触发微信位置接口与敏感个人信息全链路；GPS 单点上报（B1）与顾客端实时地图点（B2）在**平台门 + 隐私门 + 室内精度门**三重成本下，本期不推荐。

1. **需求粒度变了，结论就可以变**【推断】：旧文否证的是"实时轨迹/持续定位"；本次用户已把粒度降到**楼栋级时点**（"不需要到室内场景，只需要定位到哪一栋"）。信息粒度从"连续轨迹"降到"单点楼栋"后，出现了一条**完全不采集设备位置**的路径（§6 B0），旧文"不做 GPS"的结论在 GPS 这一档仍然成立（§6 C）。
2. **触发窗口客观存在且短**【仓内】：订单状态机里唯一有配送语义的窗口是 `PICKED`（已取件·配送中，CONTRACT §5 状态表），窗口两端已有服务端时间戳 `pickedAt`/`deliveredAt`；v1.0 订单模型是「一单多包裹、取件为订单级动作」，所以"订单全部取件完成"=该单这一次 `PICKED` 转移，不需要任何聚合（§2.1）。顾客端 10s 轮询（§2.2）意味着任何"实时移动点"最多 10s 一跳，产品上只能是"当前在哪"而非"轨迹"。
3. **平台门的关键事实（v2 修正旧表述）**【官方】：`wx.getLocation` 的国内主体开放类目表里，「工具」确实开放了二级类目**天气、信息查询、办公、设备管理**（原文见 §3.2）。因此旧文"工具类目大概率拿不到"的措辞**不准确**：白名单行在，真正的风险是①申请时填写的"应用场景"必须与类目一致，而本需求场景属配送/履约而非"信息查询"；②个人主体后台可选子类目属【未取证】；③提审会检测声明与代码一致性（61040）。**B0 不调用任何位置接口，平台门为 0**——这是它对 B1/B2 的结构性优势。
4. **隐私门按方案分层**【官方】：连续位置=**行踪轨迹=敏感个人信息**（《个人信息保护法》第 28 条原文列举），需特定目的+充分必要性+严格保护（28 条）、**单独同意**（29 条）、告知必要性与影响（30 条）；B1 触发全部三档，B0 只是"用户主动选择的楼栋文本"（推断：不构成行踪轨迹），代价从"重写承诺+全量重同意"降到"新增一行收集说明+可见范围+短期留存"（§4.2）。
5. **产品门：外卖类比只能借"感觉"，不能借"数据"**【推断】：外卖骑手在城市室外道路、平台有持续后台定位、主体是企业且类目是物流/餐饮；本产品兼职在**室内驿站取件、楼栋间短距离移动**，且客户端不直连数据库、实时推送不可用（§5）。楼栋级时点的可信度可以做到"说的是实话"，但做不到"画一个会动的点"。
6. **推荐（P1，需裁决）**：只做 **B0 + A 档文案**——兼职在配送窗口内点一次「我到 X 苑 Y 栋了」（候选楼栋由系统给，不允许自由输入），顾客订单详情显示"兼职已到 D4 栋（3 分钟前）"；数据覆盖式、终态即清、不留历史，后台/日志/通知零位置。
7. **P0（无需裁决、可先做）**：A1 现有状态卡 + A2 文案增强（"已取件 X 分钟""通常用时区间"），把"在配送中"讲清楚；不新增任何信息类型。
8. **P2（预留，需再次裁决）**：B2 顾客端只读地图（静态楼栋点位 + 当前楼栋标记，不做路线规划、不做实时移动点）；B1 单点 `getLocation` **本期关闭**，仅当平台类目/接口可开通**且**有真机精度证据时重开评估。
9. **纪律红线**：B0 上线前必须**先改文本再改代码**（CONTRACT §11.1 措辞澄清、隐私指引、UX 三端、DATA_MODEL、QA）；正式 D 编号由 Lead 在裁决后按序分配，本文占位 `R-DEC-31`~`R-DEC-38`（§8.3），不假装已裁决。**本文不代宣布任何真机/类目/审核/法务结论。**

## 2. 现状与触发口径（顾客端"检测到全部取件完成"到底指什么）

### 2.1 仓内事实：v1.0 订单是「一单多包裹」，取件是订单级动作

【仓内】批 10 已把订单主表从"单包裹"升级为 v1.0「一单多包裹」（CONTRACT §13 表内 v1.0 增补项；§4 `orders` 行、§5.2「截图与订单关系（v1.0 修订）」、§5 状态机附注）：

- 一个订单 = **1~10 件包裹**（`order.parcels[]`），可来自 **0~5 张截图**（`order.images[]`；含 `manualEntry=true` 的无截图手填单）；
- 同一顾客 + 同一绑定兼职、在 `config.orderMergeWindowMinutes`（默认 10 分钟，0=关闭）内、且**配送地址相同**的提交会自动并入同一订单（合并窗口）；不同地址各自成单；
- **订单级动作（接单/取件/送达/取消/超时）作用于全部包裹**，不设包裹级状态；`order.correct` 按 `itemIndex` 逐包裹纠正；
- 新增**每单配送地址** `order.delivery{zone,buildingNo,room,dormKey,buildingText,recipientName?,phoneTail?}`（默认=下单人宿舍，但可改为他人宿舍，即"互送"场景）；`order.dorm` 保留为下单人宿舍快照。

【推断】**这把"订单全部取件完成"的语义彻底简化了**：不再需要跨单/跨包裹聚合，它就是**订单级 `PICKED` 这一次状态转移**——与 §2.3 的窗口定义天然一致。

| 读法 | v1.0 下的含义 | 本文取舍 |
| :-- | :-- | :-- |
| (a) 订单取件完成 | 该单 `status=PICKED`（该单全部包裹一起取到） | **采纳**：位置块按订单展示，窗口=该单 `PICKED` |
| (b) 顾客短时间内多次提交 | 合并窗口内已并入同一订单（配送地址相同才合并） | 无需额外聚合；地址不同各自成单、各自独立窗口 |
| (c) 顾客名下多张进行中订单 | 合并窗口关闭、或配送地址不同时可能出现 | 不做**跨单位置聚合**（跨单位置会暴露他人楼栋，§4.3）；列表页顶多做"共 N 单配送中"计数 |

### 2.2 "检测"发生在服务端，不在页面层

【仓内】CONTRACT §12："页面层零业务判据"；`docs/V4_UX_CUSTOMER.md:287`：订单详情 10s 轮询（`onShow` 起 / `onHide` 停）+ 下拉刷新 + `serverTime`；`:542`（§8.1）：失败 20s→40s 退避。

【推断】因此"顾客端检测到"应实现为：**服务端在订单 DTO 里决定是否附带位置块**，页面只渲染；轮询间隔决定了位置最多 10s 刷一次（退避时 20~40s），**任何方案都不应承诺"实时"**。

### 2.3 触发窗口定义（可直接落判据）

| 项 | 定义 | 依据 |
| :-- | :-- | :-- |
| 开窗 | `order.markPicked` 成功、`status` 由 `ACCEPTED`→`PICKED`，服务端写 `pickedAt`（v1.0：本次动作覆盖该单**全部包裹**） | 【仓内】`cloudfunctions/api/handlers/order/markPicked.js:25`（`set:{pickedAt}, toStatus:PICKED`）；CONTRACT §5 状态表 |
| 关窗 | `status` 离开 `PICKED`：`DELIVERED`/`COMPLETED`/`CANCELLED`/`EXCEPTION` | 【仓内】CONTRACT §5 状态表；`shared/order-state.js` |
| 异常分支 | `EXCEPTION.fromStatus=PICKED` 时**不展示位置**（异常中位置不可信，且避免"被盯着"的观感） | 【推断】；异常语义见 CONTRACT §5 状态表 |
| 撤销回退 | `order.unmarkPicked`（`PICKED→ACCEPTED`）立即关窗；`order.unmarkDelivered`（`DELIVERED→PICKED`）按状态**重新开窗** | 【仓内】CONTRACT §5.1 补偿与纠正动作；UX_CUSTOMER `:453`~`:454` |
| 兜底超时 | 兼职忘记点送达时，位置块最多展示到 `pickedAt + TTL`；TTL 取 `config` 可配项，**不写死数字**（由裁决确定后进 `config`） | 【推断】；配置模式同 `config.orderTimeoutMinutes`（CONTRACT §5.2 超时口径） |

## 3. 平台门（外部事实，逐条核对官方文档）

### 3.1 位置接口的授权链（官方原文）

【官方】[wx.getLocation 官方文档](https://developers.weixin.qq.com/miniprogram/dev/api/location/wx.getLocation.html)：

- **类目准入**："暂只针对如下类目的小程序开放，需要先通过类目审核，再在小程序管理后台，「开发」-「开发管理」-「接口设置」中自助开通该接口权限。……并从 4 月 18 日开始，在代码审核环节将检测该接口是否已完成开通，如未开通，将在代码提审环节进行拦截。"
- **声明义务**："自 2022 年 7 月 14 日后发布的小程序，若使用该接口，需要在 app.json 中进行声明，否则将无法正常使用该接口。"
- **授权与能力**：需要 `scope.userLocation`；仅**前台**可用（"当用户离开小程序后，此接口无法调用"）；坐标 `gcj02` 才能配合 `wx.openLocation`/`map`；基础库 `2.17.0` 起有**调用频率限制**。

【官方】[小程序地理位置接口申请与使用指引](https://developers.weixin.qq.com/doc/oplatform/Third-party_Platforms/2.0/product/apply_privacy_api.html)：

- "如果小程序在代码中使用了地理位置相关接口，但未申请对应权限或未按照开发文档在 `requiredPrivateInfos` 中声明，都将无法提交代码审核。"
- `requiredPrivateInfos` 配置示例原文：`{"requiredPrivateInfos":["onLocationChange","startLocationUpdate"]}`。
- **61040**：代码用了接口但未在 `ext_json` 配置 `requiredPrivateInfos` / AppID 未获得该接口权限 / 配置了但无权限——三种原因都会被拦；**61039**：上传后检测未结束即提审。

【官方/官方转载】隐私授权链：自 **2023-10-17** 起，涉及处理用户个人信息的小程序，**仅当开发者向平台同步用户已同意小程序隐私保护指引后，方可调用对应隐私接口**；且需在平台《小程序用户隐私保护指引》中声明所处理的用户个人信息类型（官方入口 [小程序隐私协议开发指南](https://developers.weixin.qq.com/miniprogram/dev/framework/user-privacy/PrivacyAuthorize.html)；本条经腾讯云官方文档对微信公告的转载核对）。

### 3.3 对 D13（个人主体 + 工具类目）的判定

| 判定项 | 事实/推断 | 结论 |
| :-- | :-- | :-- |
| 工具类目是否在 `getLocation` 白名单 | 【官方】"工具"行开放二级类目 天气/信息查询/办公/设备管理 | **是**——旧文"大概率不匹配"表述需修正 |
| 本需求场景能否写进"信息查询" | 【推断】本需求是配送履约透明，与"潮汐/海拔/天气查询"语义不同；申请时要填写应用场景，审核按真实场景判断 | **场景陈述不符风险高**，不能靠换词通过 |
| 个人主体能否选到这些子类目 | 【未取证】个人主体可选类目以微信后台为准；D13 已裁决"提审前在后台确认"（CONTRACT §2 核心架构 D13 条、§13 D13 行） | 需用户在后台取证（§10.4） |

**结论**：平台门不是"文档级硬禁止"，而是**审核判定风险 + 场景陈述风险 + 个人主体可选性未知**三者叠加；而 **B0 不调用任何位置接口**，因此不受本节任何一条约束（不需要 `requiredPrivateInfos`、不需要 `scope.userLocation`、不需要后台接口开通、不需要在微信后台声明"位置信息"）。

### 3.4 地图组件（B2 相关）

【官方】[map 组件文档](https://developers.weixin.qq.com/miniprogram/dev/component/map.html)：原生组件；经纬度必填，坐标系为 **gcj02**；marker/polyline/circle 等属性；"个性化地图"属另外的能力（文档提到地图鉴权错误码 `-100~-500`、`1400001` 等）。**组件文档未列出类目准入或定位权限要求**。

## 4. 隐私门（法定事实 + 本仓改判代价）

### 4.1 个人信息保护法定级（官方原文）

【官方】《个人信息保护法》（政府政务公开站全文节选）：

- **第二十八条**："敏感个人信息是一旦泄露或者非法使用，容易导致自然人的人格尊严受到侵害或者人身、财产安全受到危害的个人信息，包括生物识别、特定身份、医疗健康、金融账户、**行踪轨迹**等信息，以及不满十四周岁未成年人的个人信息。只有在具有特定的目的和充分的必要性，并采取严格保护措施的情形下，个人信息处理者方可处理敏感个人信息。"
- **第二十九条**："处理敏感个人信息应当取得个人的**单独同意**；法律、行政法规规定处理敏感个人信息应当取得书面同意的，从其规定。"
- **第三十条**：处理敏感个人信息还应"向个人告知处理敏感个人信息的**必要性以及对个人权益的影响**"。

【推断】连续位置/多点位置序列构成"行踪轨迹"→ 敏感个人信息，触发 28/29/30 全部要求；**单个、由用户主动选择、覆盖式、仅配送窗口存在的楼栋文本**，从"信息可识别性 + 使用目的 + 影响程度"看更接近一般个人信息（位置相关信息），不构成"轨迹"——但这属于法务判断，本文只给论证，**最终由用户裁决定级**（R-DEC-32）。

### 4.2 本仓现行承诺与改判代价（三档）

【仓内】现行硬口径：

- CONTRACT §11.1 末尾：「**永不收集**：完整手机号、通讯录、**定位**、身份证、麦克风、微信好友关系；不收集用户相册里的其他照片」。
- CONTRACT §11.1 收集清单表（当前 17 行）**没有"位置"行**——任何位置类信息都是新增信息类型。
- CONTRACT §11.2：「**重大变更（新增信息类型、扩大用途、对外提供）**……必须披露……上线前先定稿《用户隐私保护指引》与《用户协议》文本」。
- `docs/privacy/发布前填写清单.md:47`：位置信息"**不使用**"、不勾；`:68`：扫描判据"无营销/定位/通讯录接口"。`docs/privacy/隐私保护指引.md` §二也明写"不收集……定位"。

| :-- | :-- | :-- | :-- | :-- |

### 4.3 无论哪一档都必须写死的红线（最小化）

1. **可见范围**：仅「本单顾客 + 该单兼职本人」；**开发者后台、只读视角、通知、分享卡片、日志一律不出现位置原值**（后台顶多看到"是否开启"布尔；即便 B1 也只给楼栋文本，不给坐标）。
2. **不留历史**：覆盖式只存"最新一次"，不写 `order_events`、不入匿名化历史、不做轨迹、不做跨订单派生（跨订单会暴露他人楼栋，§6.2 明确排除）。
3. **窗口内生存**：离开 `PICKED` 立即清除；兜底 TTL 到期清除；注销/删号路径同步清除（`cleanup` 与 `user.deleteAccount` 链路）。
4. **不采集多余**：B0 不存坐标/精度/速度/设备信息；B1 若启动也只回楼栋文本，原始坐标按裁决最短留存后删除。
5. **可撤回**：兼职可关闭共享，关闭后订单详情显示"兼职未开启位置共享"，不影响接单与送达（R-DEC-34）。
6. **客户端零新增外呼**：不得为位置引入任何第三方地图 SDK/LBS KEY（AGENTS §4.4、ENGINEERING 门禁）。

## 5. 产品门（与外卖的类比到底差在哪）

| 维度 | 外卖骑手定位 | 本产品（校园快递代取） | 影响 |
| :-- | :-- | :-- | :-- |
| 移动场景 | 城市道路/室外，GPS 可用 | **驿站常在楼内（如三楼）、宿舍楼内**；楼栋间距离短 | 室内漂移大：**最需要准确的位置恰是信号最差的位置**（旧文 R27 保留） |
| 连续性 | 平台有后台持续定位，地图上连续移动 | 客户端不直连数据库/无实时推送；只有 10s 轮询 | 只能"当前在哪"，画不出"会动的点" |
| 展示粒度 | 街道级实时点 + 预计送达 | 用户已降到**楼栋级** | 粒度匹配可行方案（B0），不匹配 GPS 方案（B1 的高成本换低可信度） |
| 主体与类目 | 企业主体 + 物流/餐饮类目，接口权限与场景匹配 | **个人主体 + 工具类目**（D13） | B1 场景陈述不符风险（§3.3） |
| 履约链 | 骑手 → 顾客，两点直达 | 兼职 → 多单批量取件 → 多栋送达 | 一个兼职同时服务多单，位置天然是"多点/多栋"，跨单展示会暴露他人楼栋 |
| 用户预期 | "实时位置"是行业默认 | 用户原话只要求"哪一栋" | 文案必须主动管理预期："最近上报的楼栋"，不是"实时位置" |

【推断】产品结论：**楼栋级时点**与用户原话匹配，且能在现有状态机/轮询/隐私框架内实现；"实时移动点"既超出现有实时链路能力，也要付出平台与合规代价，收益（顾客多看到一个会动的点）不匹配成本。

## 6. 候选方案矩阵

### 6.1 方案 A：状态驱动（零定位）——A1/A2 可做，A3 不做

| 子档 | 触发时机 | 数据字段 | 权限/平台门 | 合规 | 实现成本 | 精度/可信度 | 失败兜底 | 结论 |
| :-- | :-- | :-- | :-- | :-- | :-- | :-- | :-- | :-- |
| **A1 现有状态卡** | 详情页任意状态 | 无新增（`status/statusText/progressIndex/pickedAt` 等已在 DTO） | 无 | 无 | 零 | 高（服务端真值） | 已有 | **现状，保留** |
| **A2 已用时/通常用时** | `PICKED` 窗口 | 无新增字段：服务端用 `pickedAt` 与 `serverTime` 算"已取件 X 分钟"；"通常用时区间"由历史 `pickedAt→deliveredAt` 聚合（同苑/同站点，样本不足不显示，数值**不写死**，取数方式给命令） | 无 | 无（聚合统计不含个人位置） | 低（1 个纯函数 + 1 处文案 + 单测） | 中（统计口径决定可信度，需标注"历史平均"） | 样本不足→只显示已用时 | **P0 推荐** |
| A3 跨订单派生"最近送达楼栋" | `PICKED` 窗口 | 需读同兼职其他订单的 `dorm` 快照 | 无 | **暴露他人楼栋**：把别的顾客的宿舍楼作为"兼职位置"展示给本顾客 | 中 | 中 | — | **不做**（§4.3 红线 2；R-DEC-35） |

> A2 的取数口径：`orders` 按 `partnerId + dorm.zone + parcel.stationId` 过滤、`status∈{DELIVERED,COMPLETED}`、取 `deliveredAt - pickedAt` 的中位数，样本数低于阈值不展示；数值只由服务端下发，前端不推算（CONTRACT §12 页面层零判据）。**具体阈值进 `config`，不写死。**

### 6.2 方案 B0：兼职关键节点主动自报楼栋（零 GPS，推荐）

**交互设计（兼职端）**：在 `PICKED` 窗口内，兼职在工作台/订单详情看到「上报我在哪栋」按钮 → 弹出**候选楼栋列表**（来自该订单 `delivery`（本单配送地址，v1.0 新增；互送场景即收件人楼栋）/`dorm`（下单人宿舍快照）/`guest`（代客单）的苑 + 楼栋，再并上同苑楼栋白名单/`config` 楼栋表）→ 点选提交。**不允许自由输入文本**（防乱填、防注入、防把"位置"变成自由文本泄漏）。

| 项 | 设计 |
| :-- | :-- |
| 触发时机 | 仅 `status=PICKED` 且订单归属该兼职；v1.0 一单多包裹时**按订单上报一次**即覆盖该单全部包裹；若同批订单的配送地址不同（多栋互送），按订单分别上报 |
| 数据字段（草案） | `orders.presence = {zone, buildingNo, buildingText, source:'SELF_REPORT', at}`；**覆盖式**，不追加数组、不留历史 |
| 写入约定 | 只由订单归属兼职写；`version` 与乐观锁策略两种选型见 R-DEC-33；**不写 `order_events`**（不把事件枚举从 16 扩成 17） |
| 校验 | 订单归属（`FORBIDDEN`）；状态必须 `PICKED`（`INVALID_TRANSITION`）；楼栋必须在候选集合（`VALIDATION_FAILED`）；限频（`RATE_LIMITED`，沿用现有 13 个错误码，**不新增错误码**） |
| 权限/平台门 | **零**：不调 `wx.getLocation`、不需要 `requiredPrivateInfos`、不需要 `scope.userLocation`、不需要后台接口开通 |
| 合规 | 位置相关信息（自报、无坐标、单点、覆盖、窗口内）；需端内文本新增 + 兼职首次提示 + 可关闭（§4.3、R-DEC-32/34） |
| 实现成本 | 中低：1 个 order 域动作 + 1 个字段 + DTO 一块 + 双端各 1 处 UI + cleanup 钩子 + 负向测试/selftest + 8 处文档回写；无新集合、无新索引、**DTO 零额外查询**（字段就在订单文档里，10s 轮询成本不变） |
| 精度/可信度 | 高（用户本人点的，不会"指错楼"）；但**依赖兼职肯点**，覆盖率是最大风险（R36） |
| 失败兜底 | 未上报→"兼职暂未上报位置，可留言联系"；过期→"X 分钟前在 Y 栋"并置灰；异常/撤销/终态→立即隐藏；兼职关闭→"兼职未开启位置共享"；网络失败→不阻断取件/送达主链路，卡片降级为状态文案 |

**为什么不做"自动派生"**：唯一能做到"零额外点击"的自动信号是"送达某单时自动知道在该单楼栋"，但把这栋楼展示给**另一单**的顾客就暴露了他人楼栋（§4.3）；在本顾客自己的单上，送达事件本身就是窗口结束信号，无中间信息。**结论：B0 必须接受"一次手动点击"**，用文案与提醒降低漏报。

### 6.3 方案 B1：关键节点单次 `getLocation`（本期不推荐）

| 项 | 设计 |
| :-- | :-- |

### 7.3 顾客 DTO 与页面（草案）

- `order.get`（及 `listCustomer` 的详情态）增加 `presence` 块：**仅当 `status=PICKED` 且调用者是本单顾客**时下发；文案由服务端给（例如 `"兼职已到 {buildingText}"`、`"{n} 分钟前上报"`），前端零判据。
