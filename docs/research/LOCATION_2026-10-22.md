## 1. 结论先行

1. **本期（P0）不做实时 GPS 追踪，也不做任何定位采集**；"定位"继续留在 CONTRACT §11 的"永不收集"清单里。方案 A（不做/状态驱动）是唯一不需要任何裁决与改动的档位。
2. 物理与产品层面首先是否证：**驿站（如"三楼"）、宿舍楼内都是室内场景，GPS 漂移大**，"实时位置"很可能把兼职画到隔壁楼，反而制造纠纷；而现有状态机已经给出"人在驿站/人在宿舍楼下"的强语义节点（§2.3）。
3. 平台层面有三道硬门（§3.1）：**位置接口只对白名单类目开放**（工具类目在 `getLocation` 下只开放"天气/信息查询/办公/设备管理"，`startLocationUpdateBackground` 下只开放"健康管理"）→ 与 D13「个人主体+工具类目」大概率不匹配；**后台定位**还要求 `requiredBackgroundModes: ['location']` 且正式版需审核；代码未声明/未开通会被提审拦截（61040）。
4. 合规层面：连续位置即**行踪轨迹**，属《个人信息保护法》**敏感个人信息**（第 28 条），需**单独同意**（第 29 条）、必要性告知（第 30 条）、**事前影响评估**（第 55 条）、最短留存（第 19 条）——相对现有所有数据（含 L3）敏感度更高（§3.1 表 2、§5.3）。
5. 工程层面：需先破 CONTRACT 隐私承诺（先改文本再改代码），再新增集合/动作/索引/门禁/清理/QA/隐私文本，且客户端"实时推送"在本仓"客户端不直连数据库"铁律下不可用，只能沿用现有轮询（§2.5、§4.2）。
6. **推荐折中（P1，可选）**：只做"**状态驱动的位置语义**"——订单详情卡片按状态显示"已到 P4 驿站 / 配送中 / 已送达 + 时间"；若一定要"地图感"，用**固定点位只读地图**（坐标由运营配置，绝不采集用户位置）。无需定位权限、不产生新的个人信息、不改隐私承诺主体（§3.2 的 B0 档、§4.1）。
7. **若用户坚持真实位置（P2 预留）**：只接受 **B 档"关键节点单次上报"**（标记已取件 / 标记送达各一次，随动作上报），不做前台持续（C）、不做后台持续（D）、不做第三方地图 SDK（E）。
8. 任何真实位置方案都必须**先改 CONTRACT/隐私文本、并经用户裁决**（占位编号 R-DEC-23 起，约定见 §5.0），代码改动一行都不许抢跑（AGENTS §1.3、CONTRACT §14 第 6 条）。**本文不代宣布真机/类目/审核通过。**

### 2.3 状态机里的"位置语义"节点（现状已经能表达什么）

【仓内】订单七状态与动作由 `shared/order-state.js:18`~`:86` 唯一定义（TRANSITIONS + ACTION_RULES）。与位置相关的节点如下，**每个节点都已有服务端时间戳，但没有坐标**：

| 状态/动作 | 仓内依据 | 天然位置语义 | 已有数据 | 缺什么 |
| :-- | :-- | :-- | :-- | :-- |
| `SUBMITTED` 下单 | `order-state.js:31`~`:36`（`order.create`）；`CONTRACT:298` | 位置语义在顾客侧（送货地址），**不是兼职位置** | `orders.dorm`/`guest` 快照、站点 `stationId` | — |
| `ACCEPTED` 接单 | `order-state.js:37`~`:39`；`CONTRACT:299` | 兼职"接下了"，**位置未知** | `acceptedAt` | 坐标（若要做"最后位置"起点） |

| `clientRequestId` | string | 是 | 幂等键（同 `partnerId` 唯一） | 同上 | 内部 | L2 |
| `isTest` | boolean | 是 | 服务端按参与账号派生（测试数据清理用） | 同上 | admin/测试会话 | L1 |
| `createdAt` | Date | 是 | 服务端时间（清理锚） | 同上 | 内部 | L1 |

**索引草案**：`uk_req(partnerId, clientRequestId, unique)`（幂等）；`idx_order_at(orderId, reportedAt desc)`（读最新）；`idx_created(createdAt)`（到期清理）；`idx_is_test(isTest, createdAt)`（测试数据清理）；**不建** `partnerId+createdAt` 之外的"轨迹"查询索引（不提供轨迹回放）。

**动作草案（新增 client action，需 `shared/actions.js`/CONTRACT §5.3 同步）**

- `order.reportLocation({orderNo, node, lat, lng, accuracy?, clientRequestId})`，写动作、必传幂等键。
- 服务端校验：身份=该订单兼职且订单 ACTIVE；`node` 必须等于当前状态（`ACCEPTED`/`PICKED`/`DELIVERED` 三选一，`DELIVERED` 后拒收）；`orderId` 归属校验；坐标范围；`accuracy` 上限；最小上报间隔（`config`）；每单**每个节点最多一条**（同节点重复上报幂等丢弃或覆盖；具体语义需裁决）。
- 错误码：沿用现有 13 码（`FORBIDDEN`/`INVALID_STATE`/`VALIDATION_FAILED`/`RATE_LIMITED`），**不新增错误码**（与 AI 兜底同纪律）。
- 限流：`counters.rl:location:{openid}:{day}`（走统一限流键族，`DATA_MODEL:624`）。

**读取与可见范围**

- `order.get` 内联 `location{lat,lng,accuracy,reportedAt}`（**仅最新一条**，不返回历史序列——目的限定，避免变成轨迹查询）。
- 可见：**该订单的顾客 + 该订单兼职本人**；不向其他绑定顾客、其他兼职、后台列表、开发者只读视角外的任何入口返回；`admin.*` DTO **零坐标**（后台脱敏铁律 `ENGINEERING:771`~`774` 门禁 #29/#30 同精神）。
- 展示上限：顾客端只看"当前订单"的位置；订单终态后不再返回并清理。

**上报频率（设计约束，不写死数值）**

- 只随动作上报：`markPicked` 成功前（或成功后紧邻一次）上报 `PICKED`；`markDelivered` 同理；`accept` 可选。**上限 = 每单 ≤3 次**。
- 服务端最小间隔与坐标精度上限进 `config.locationCapture`（出厂默认关；MVP 后台只读，同 `aiFallback` 口径：改值走部署配置且必须与隐私文本同步）。
- 明确**不做**：定时上报、心跳、持续监听、轨迹点序列、后台采集。

**留存/注销/清理钩子（必须四处同步）**

| 钩子 | 改动点 |
| :-- | :-- |
| 到期清理 | `cloudfunctions/cleanup/sweeps/index.js:16`~`:30` 新增 sweep（如 `locationRetention`），`config.locationCapture.retentionHours` 到期删整条或清坐标 |

**负向测试清单（DATA_MODEL §12 扩展草案）**：兼职 A 上报兼职 B 的订单 → `FORBIDDEN`；顾客读非自己订单的 location → `FORBIDDEN`；终态订单上报 → `INVALID_STATE`；同 `clientRequestId` 重放 → 幂等不新增；超频 → `RATE_LIMITED`；`accuracy` 超上限/坐标越界 → `VALIDATION_FAILED`；匿名化后坐标为空；注销后查询为空；测试单 `isTest` 记录不进真实视图。
